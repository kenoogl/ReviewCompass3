# ReviewCompass3 計画 統合最新版

## 1. 位置付け

本文書は、ReviewCompass3の再構築計画、開発方針改定、Task Contract中心構想、既存37要件、
追加13要件、設計改定、旧第5段継承判断を、現在有効な一つの計画候補へ統合したものである。
過去文書は履歴とEvidenceとして保持し、本文書は現在の作業順、責務、関門、初期範囲と
deferred範囲を通読するための参照点とする。

Intentの正本候補は`docs/current/reviewcompass3-intent-current.md`であり、本文書はその内容を
変更しない。Intent、Requirements、Task Contract、Architecture Policy、Design Decision、
実装の順にauthorityを下げる。本文書はHuman承認前であり、第5段完了または実装開始の承認を
代替しない。

## 2. 現在地と固定baseline

### 2.1 現在地

- Work 1B、Work 2、Work 3は`verified / completed`であり、当初順序上の次工程はWork 4である。
- Work 3完了後、Work 4開始前に、session transcript保全、配置境界、Issue Resolution早期Pilot、
  commit／handoff安定化をinter-work correctiveとして挿入した。
- 完了済みcorrectiveはSession Records、Work 7またはWork 8全体の完了を意味しない。未完了の
  Issue Resolution早期Pilot bootstrapを限定して終えた後、Work 4へ戻る。
- 第0段から第2段のbootstrap実装、test、Evidenceを保持している。
- 2026-07-27のIntent、Feature Partitioning、37 requirementsを固定baselineとして保持する。
- 2026-07-28の第5段design候補、9 design、29 interface、8 state machine、14 protocol、
  37 acceptance testは`awaiting_human_approval`である。
- 2026-08-02に開発方法を製品Intentから分離し、リスクベースのtest-firstへ改定した。
- Task ContractをRequirementsとRuntimeのcontrol and provenance planeとする後継候補を
  追加した。
- 旧第5段候補は承認済み正本へ昇格しておらず、Task Contract差分と継承監査を反映した
  新しい承認候補が必要である。

### 2.2 上書きしないEvidence

- ReviewCompassとReviewCompass2の固定commit、code、test、仕様、失敗事例
- 既存37 requirementsとcoverage audit
- 旧第5段の構造化design、architecture integrity、acceptance test
- LLMGPのSDD/TDD hybrid試行
- ReviewCompass2の変更規模比例review入力、決定的slice、残余riskとしての全文整合review
- ReviewCompass2の共通routine台帳とIssue→Plan実績
- ReviewCompass2のfreeze原因、実装済みsession capture、validator／review品質の横断知見
- ReviewCompassのconformance-evaluation要件、設計、実装
- 各変更判断とartifact Digestを持つTask Contract documentation record

前身成果は現在の正本として一括移植せず、`preserve | adapt | replace | defer`で判断し、
replaceでも安全義務、failure verdict、永続化順序、後継owner、後継testを失わない。

## 3. 製品構成

### 3.1 Feature

既存9 Featureを維持し、Task Contract Controlを追加する。

| Feature | 主責務 |
|---|---|
| `FEAT-TASK-CONTRACT-CONTROL` | Contract schema、Portfolio、Compiler、Policy解決、Plan bundle、被覆、stale閉包 |
| `FEAT-REVIEW-CONTEXT` | Task criteria、Target、materials、Scope、Context identity、stale、handoff |
| `FEAT-HARNESSED-EXECUTION` | Run、Attempt、外部送信、raw capture、validation、retry、観測 |
| `FEAT-REVIEW-TRIAGE` | 担当別結果、重複、競合、Finding、Decision Record（初期はHuman採否） |
| `FEAT-SEMANTIC-TRACE` | 意味単位、型付き関係、双方向被覆、影響閉包、Operational Provenance |
| `FEAT-SESSION-RECORDS` | 許可範囲のSession取込み、raw保全、伏字化派生、要約、mutation |
| `FEAT-WORKFLOW-CONTROL` | Work routing、状態、Run permit、block、resume、termination、write permit、scheduler policy、競合制御 |
| `FEAT-PORTABLE-LIFECYCLE` | 論理root、構造化I/O、install、update、uninstall、retention |
| `FEAT-EVIDENCE-EVALUATION` | 評価基準、観測、Outcome Label、metric projection、解釈限界 |
| `FEAT-SELF-IMPROVEMENT` | 固定比較、改善仮説、権限付き判断、ownerへの版付きProposal |

Cross-Contract Integration、Issue Resolution、As-Built projectionは独立した大域Stageまたは
初期新componentにせず、既存owner間の能力として設計する。不足が実測されるまで汎用的な
新componentを追加しない。

### 3.2 component state ownership

- Task Contract Control：Contract definition、Portfolio、compile、Policy解決
- Context Runtime：Review Context FeatureのContext候補採否、Scope、Context identity
- Workflow：Work Item、routing、permit、block、resume、termination、scheduler policy、owner／lease、競合制御
- Harness：Run、Attempt、送信、raw capture、validation、retry
- Triage：Finding候補、duplicate、conflict、判断候補とDecision Record
- Semantic Trace：意味グラフ、被覆、影響閉包、Provenance検証
- Session Evidence Source：session取込みと派生物
- Portable Lifecycle：配置、原子的I/O、migration、data保護
- Evidence Evaluation：評価projectionと限界
- Self Improvement：改善Proposalと次trial

ContractとCompilerはPlanを提供するが、consumerの状態を直接変更しない。Workflowは
RequirementまたはContract本文を直接変更せず、上流authorityへRevision Proposalを返す。

## 4. 現行Requirements

既存37要件と追加13要件の計50要件を現行差分母集合とする。各要件の詳細な入力、出力、
停止、復旧、保存、受入、対象外は生成元requirementsに保持し、本文書では現在の意味と
ownerを固定する。

### 4.1 Review Context：7要件

- `REQ-CONTEXT-001`：Goal、Target、Constraints、Expected Output、Context、Validation、
  Provenanceを持つ版付きTask入力を固定する。
- `REQ-CONTEXT-002`：Targetとsource materialを本文、役割、出所、Digest付き材料束にする。
- `REQ-CONTEXT-003`：母集合、include、exclude、defer、未分類、競合をScope contractにする。
- `REQ-CONTEXT-004`：Context identityと入力変更後のstaleを検出する。
- `REQ-CONTEXT-005`：候補の採用、除外、順序、制約をContext Compositionとして固定する。
- `REQ-CONTEXT-006`：再開時にprior成果、未解決、次作業をhandoffする。
- `REQ-CONTEXT-007`：失敗記録を安全な共有保存境界へ残す。

Task Contract導入後、`REQ-CONTEXT-001`のReview Task定義はContractのContext obligationと
compiled Context Acquisition Planへ責務を移し、Context自身は取得・採否・freshnessを所有する。
`REQ-CONTEXT-003`と`005`は、`REQ-TRACE-004`が変更単位、版付き意味graph、閉包規則から生成した
影響候補を全件分類する。review入力は影響閉包、必要なEvidence抜粋、Contract必須材料から構成し、
無関係な文書総量を入力の支配要因にしない。

### 4.2 Harnessed Execution：6要件

- `REQ-EXEC-001`：Workflow許可と固定実行仕様に一致するRunだけを開始する。
- `REQ-EXEC-002`：payload、capability、送信先、承認者、権限、期限を送信identityへ束縛する。
- `REQ-EXEC-003`：response受領とraw captureを分け、解析前にwrite-ahead保存する。
- `REQ-EXEC-004`：複数担当とround結果を欠落なく保持する。
- `REQ-EXEC-005`：形式復旧を閉じた変換またはHuman裁定へ限定する。
- `REQ-EXEC-006`：実行条件、観測、費用、再試行、再利用根拠を不変記録する。

### 4.3 Triage：3要件

- `REQ-TRIAGE-001`：担当別結果を件数と結論を失わず要約する。
- `REQ-TRIAGE-002`：複数modelの重複、競合、独立所見と元Findingを保持する。
- `REQ-TRIAGE-003`：Human採否を対象内容とDigestへ束縛し、Provenance関門後に確定する。

### 4.4 Semantic Trace：5要件

- `REQ-TRACE-001`：意味単位と関係を閉じた語彙とIDで固定する。
- `REQ-TRACE-002`：上流義務と下流成果を順逆追跡し、未被覆を拒否する。
- `REQ-TRACE-003`：共有data境界を決定的validatorでfail-closedにする。
- `REQ-TRACE-004`：変更単位、意味関係、閉包規則から影響候補母集合を生成する。
- `REQ-TRACE-005`：Task入力からFindingまでのOperational Provenance verdictを生成する。

Trace対象はRequirement、Contract obligation、Plan、Context、Execution、Result、Evidence、
Human判断へ拡張する。
`REQ-TRACE-004`の出力には候補だけでなく、変更起点から各候補へ到達した関係と閉包規則を含める。

### 4.5 Session Records：3要件

- `REQ-SESSION-001`：利用者が明示したsource universeだけを取り込む。
- `REQ-SESSION-002`：rawを保全し、伏字化転写、要約、来歴へ結ぶ。
- `REQ-SESSION-003`：追記、非追記変更、消失を区別しmutationを検出する。

raw、派生物、要約は別identity、access、retention、削除Policyを持つ。Session obligationを
持たないContractはSession未取込みだけで停止しない。
sourceの実効retention、capture deadline、取得時点、復元方法、復元検証を記録し、
`source_missing | source_expired | non_reconstructable`を正常な空結果と区別する。必須sourceの
復元は参照の存在だけでなく、期待Digest、構造、派生物再生成まで確認する。

### 4.6 Workflow：既存4要件と追加5要件

- `REQ-WORKFLOW-001`：現在対象、Work Item、backlog、進行段階を一意IDで結ぶ。
- `REQ-WORKFLOW-002`：段階とRun開始・完了許可を状態機械で管理する。
- `REQ-WORKFLOW-003`：成果物書込みをactive Work Itemと許可actionへ束縛する。
- `REQ-WORKFLOW-004`：stableな通常契約をReviewCompass3自身にも適用できる。
- `REQ-WORKFLOW-005`：`new_development | maintenance`と`fresh | reopen`を独立にrouteする。
- `REQ-WORKFLOW-006`：TDD中の不整合を最下位変更層へ分類し上流改定を制御する。
- `REQ-WORKFLOW-007`：境界外依存、初期の単一active leaf、循環検出、親再開、および後続の
  bounded parallelに必要な安全条件を制御する。
- `REQ-WORKFLOW-008`：pause、cancel、close-scopeと未充足義務を保存する。
- `REQ-WORKFLOW-009`：green実装前にIndex、Ledger、実codeを照合し再利用判断を確定する。

`REQ-WORKFLOW-010`のIssue登録・triageと`REQ-WORKFLOW-011`のResolution Plan・Plan Challenge・
Resolution Verdictは要件候補であり、手作業Pilot前に現行50要件へ確定追加しない。

`REQ-WORKFLOW-007`の現行義務である単一active leafは初期scheduler policyとして保持する。
`bounded_parallel`、conflict domain、owner／lease、統合後のstale再判定は、Work 3で同じownerの
後継Requirement versionとして確定する。確定前に新しい要件IDまたは汎用分散schedulerを追加しない。

### 4.7 Portable Lifecycle：4要件

- `REQ-PORTABLE-001`：supported-platform matrixとlogical rootで配置を解決する。
- `REQ-PORTABLE-002`：構造化成果物を原子的に読み書きし、部分失敗から復旧する。
- `REQ-PORTABLE-003`：配布、導入、運用、更新、解除を所有境界付きで行う。
- `REQ-PORTABLE-004`：機微情報、retention、削除の共有境界を提供する。

### 4.8 Evidence Evaluation：3要件

- `REQ-EVAL-001`：固定対象へ明示基準を適用し、Evidence付き適合性を得る。
- `REQ-EVAL-002`：Harness観測へ基準を適用し、結果と解釈限界を分離する。
- `REQ-EVAL-003`：評価と分析を再現可能なpackageへ固定する。

### 4.9 Self Improvement：2要件

- `REQ-IMPROVE-001`：成功と失敗の実測を条件付き学習材料として蓄積する。
- `REQ-IMPROVE-002`：改善候補を固定比較とHuman判断後だけ次周期へ渡す。

現行WorkflowやPolicyを直接変更せず、対象ownerの通常version protocolを通す。

### 4.10 Task Contract Control：8要件

- `REQ-CONTRACT-001`：Identityと9領域を持つ版付きTask Contractを固定する。
- `REQ-CONTRACT-002`：固定Contract、Compiler、Policyから一つのbundle内の6 Plan viewを決定的にcompileする。
- `REQ-CONTRACT-003`：Portfolio被覆と変更時のstale閉包を検証する。
- `REQ-CONTRACT-004`：Conformance、Definition Challenge、Final Challengeを分離する。
- `REQ-CONTRACT-005`：Provenance obligationからCapture Planと必須eventを生成する。
- `REQ-CONTRACT-006`：Evaluation Profileを固定し一次eventからmetricを再計算する。
- `REQ-CONTRACT-007`：accepted Contract間のIntegration PlanとVerdictを生成する。
- `REQ-CONTRACT-008`：ProvenanceからAs-Built文書を投影する。後続開発であり初期範囲外。

### 4.11 AIへの判断委譲に関するRequirementsの扱い

現行50要件のうちHumanを明示する関門は、初期開発の安全な既定値として維持する。本計画だけで
`REQ-TRIAGE-003`、`REQ-IMPROVE-002`、外部送信、Stageまたはrelease判断などのauthorityを
AIへ読み替えない。

AIへの判断委譲を実装する前に、少なくとも次を独立したRequirements差分として定義し、既存
要件との順逆被覆と受入条件をレビューする。この差分は追加13要件には数えず、初期Work 1〜8と
初期releaseの範囲外とする。

- 対象業務ごとの能力評価と、委譲可能と判断する基準
- 委譲する判断class、対象、権限、期間、利用可能なmodelまたはcapabilityの固定
- 範囲外、期限切れ、根拠不足、不確実性、競合時のfail-closedとHuman escalation
- 委譲の停止、取消し、再評価と、影響を受ける既存判断のstale化
- 判断主体、能力Evidence、Delegation Authorization、入力、理由、結果のProvenance
- AIが自分への委譲範囲を作成、拡張、更新または再有効化できないこと

### 4.12 用語統制に関するRequirementsの扱い

`REQ-TRACE-001`はrelationの閉じた語彙を要求するが、製品文書全体のdomain用語統制を直接は
要求していない。統合用語集は文書作成時の規律として初期段階から使用する。用語登録、alias、
retirement、schemaとの同期をRuntimeで強制する機能は、具体的なE2E不足を確認した後に独立した
Requirements差分として定義し、追加13要件へ暗黙に含めない。

初期の文書reviewでは、次を手作業で確認し、結果を変更記録へ残す。

- 登録対象となる新しいdomain用語が、使用前または同じ変更で定義されている
- 一つの概念に複数のcanonical termを与えていない
- 日本語表示名、英語token、schema値の対応が一致する
- 旧語、alias、retired termから現行語への一方向の読み替えがある
- 意味変更時に影響文書とstale対象を確認している

### 4.13 横断AssuranceとEvidence利用に関するRequirementsの扱い

要件数50は変えず、既存のContext、Trace、Workflow、Evaluation、Task Contract要件を強化する。
既存資料の抽出はEvidence Extraction Contractで開始集合、展開規則、分類、終了条件、除外、
完全性oracleを固定する。候補全件を`adopt | adapt | reject | defer`へ分類し、必須sourceと採用
FindingをRequirement、Contract obligation、VerificationまたはDecisionへ接続するEvidence
Consumption Closureがなければ完了にしない。

重要な規則はAssurance Obligation Matrixで宣言、runtime enforcement、failure verdict、permit効果、
復旧、Evidenceを被覆する。自動validatorはValidator Assurance Profileで既知正例、負例、境界例、
mutation、独立oracleまたは代表実データを固定する。Review Quality Contractはverdict、severity、
`insufficient_evidence`、`out_of_level`、材料十分性、独立性、収束条件を固定する。書込み変更は
riskに応じたpost-write verificationを完了するまで`verified`にしない。

横断制約は`OBL-CONTEXT-EVIDENCE-EXTRACTION`、`OBL-TRACE-EVIDENCE-CONSUMPTION`、
`OBL-CONTRACT-ASSURANCE-MATRIX`、`OBL-VERIFICATION-VALIDATOR-ASSURANCE`、
`OBL-REVIEW-QUALITY-CONTRACT`、`OBL-WORKFLOW-POST-WRITE-VERIFICATION`、
`OBL-SESSION-SOURCE-AVAILABILITY`の7 sub-obligation IDで参照する。各IDは一つのprimary
Requirement、supporting Requirements、compile先、enforcement、failure、復旧、Evidence、fixtureを持つ。

## 5. 標準開発ステージ

```text
Stage A: Intent
Stage B: Feature Partitioning
Stage C: Requirements
Stage D: Task Contract Portfolio
Stage E: Task Contract TDD Delivery
Stage F: Cross-Contract Integration
Stage G: Release Evaluation
```

### Stage A：Intent

製品の存在理由、方針、委譲の可否と範囲はHumanが確定する。承認済みの上位目的の範囲内で
行う局所目的の具体化は、有効なDelegation Authorizationがある場合に限りAIへ委譲できる。
実装方法は開発方針へ置く。

### Stage B：Feature Partitioning

大域責務、owner、依存、共有境界を分ける。複数Feature競合はこの段へ戻す。

### Stage C：Requirements

外部義務、入力、出力、停止、復旧、保存、受入、対象外をatomic obligationとして定義する。

### Stage D：Task Contract Portfolio

Requirementの受け先、Contract依存、risk、cross-contract acceptanceを固定する。未被覆、
重複owner、循環を検出する。並行候補については依存だけでなく、変更対象、共有state、side effectの
競合範囲を識別し、実行予定のないContractを過剰詳細化しない。

### Stage E：Task Contract TDD Delivery

局所責務をContractとしてchallenge、compile、red、implementation discovery、green、verify、
acceptする。Design、旧Task記述、Implementationを大域stageにせずContractの実現成果とする。

### Stage F：Cross-Contract Integration

accepted Work Item間のinterface、共有state、E2E、failure propagation、配置、lifecycleを検証する。
Stage Fは全Contractの完了後に一度だけ行う段ではない。二つ目以降の関連Contractがacceptedになる
たびに対象集合へ適用する。並行実行したWork Itemは、固定した各成果と統合時のsource identityを
integration checkpointへ束縛し、baseまたは統合結果の変更後に必要な再検証を行う。Integration
Findingは変更が必要な最下位のStageへ戻す。

### Stage G：Release Evaluation

supported platform、distribution、migration、data保護、Provenance、評価比較を確認する。
初期releaseの可否はHumanが判断する。後続では、release判断classが明示的に委譲され、能力、
risk、可逆性、安全条件を満たす場合だけ、範囲を限定してAIへ委譲できる。

stageは一方向ではない。Intent、Feature、Requirement、Contract、Design Decision、
Implementationのうち変更が必要な最下位層へ戻り、旧成果を残して新versionを作る。
初回bootstrapではStage Aより前に配置baselineとSession Log Bootstrapを準備し、Stage Dから最初の
Stage Eへ入る前に関数台帳baselineを固定する。これらは新しい大域Stageではなく、以後のContractが
参照するbootstrap／実装前preconditionである。

## 6. Task Contract設計

### 6.1 Contract schema

Task ContractはIdentityと次の9領域を持つ。

1. Responsibility
2. Boundary
3. Preconditions
4. Context Obligations
5. Allowed Capabilities
6. Expected Outputs
7. Acceptance Criteria
8. Provenance Obligations
9. Escalation Policy

各obligationは配列位置ではなく一意な`obligation_id`を持つ。UTF-8、key順、型、set相当配列、
path、URI、ID、schema version、Digest algorithmを正規化する。Contract本文、challenge、Human
approvalは別recordとし、初期approvalをContract、source Requirement、challenge Digestへ束縛する。
後続で委譲を有効にした場合も、Decision RecordとDelegation AuthorizationはContract本文から
分離して保存する。

外部side effectを持つContractまたは適用Policyは、timeout／deadline、cancellation可能範囲、
idempotency identity、部分成功時のcompensationまたはreconciliation、自動回復不能時のHuman
escalationを定める。外部side effectを持たないContractへ汎用job controlを一律に要求しない。

### 6.2 Architecture PolicyとProject Overlay

複数Contract共通制約はTask Contractへ複製せず版付きArchitecture Policyへ置く。

- 原理Aとcomponent state ownership
- ID、Digest、Schema
- security、permission、external send
- Decision Authority、Human decision、Delegation Authorization
- storage、deployment、cross-contract interface
- Implementation Reuse Policy

PolicyはID、version、digest、owner、適用範囲、rule、priority、supersedes、競合解決を持つ。
project固有変更はbase Policyへ手追記せず、置換規則、理由、Evidence、決定者、期間を持つ
Project Policy Overlayへ置く。同順位競合または未解決Policyはcompileしない。

### 6.3 CompilerとPlan bundle

```text
Contract + fixed Policy + fixed Capability Resolution
  → normalize
  → validate references
  → project six typed Plan views
  → verify obligation coverage
  → verify cross-plan consistency
  → Plan bundle identity
```

導出するPlan viewは次の6種類である。

1. Context Acquisition Plan
2. Review / Execution Plan
3. Harness and Capability Plan
4. Verification Plan
5. Provenance Capture Plan
6. Human Interaction Plan

Implementation Task ContractだけはReview / Execution Plan内にImplementation Discovery Planを
持つ。これは全Contract共通の第7 Planではない。未被覆、未解決、必須Plan生成不能は
`not_compilable`とし、consumerへ開始可能Planを渡さない。

六つは一つのimmutable Plan bundle内のtyped viewであり、bundle全体に一つのidentity、version、
Digest、compile verdictを持つ。viewへ独立approval、独立lifecycle、独立state machineを持たせず、
共通fieldをbundle共通部へ一度だけ保存し、consumerへ必要なviewを決定的にprojectionする。独立した
owner、security、retention、failure recoveryまたは実測scaleがない段階で別serviceへ分割しない。

#### 6.3.1 変更規模に応じたreview入力

Context Acquisition Planの既定selection modeを`impact_slice`とする。固定変更単位から意味graphを
閉包規則どおりたどり、到達した影響候補、必要なEvidence抜粋、Contract必須材料をContextへ採用
する。「変更規模」は変更行数ではなく、この影響閉包と必須材料の規模を意味する。source universeへ
影響関係のない材料を追加した場合、freshnessは再検査するが、選択材料とreview payloadを増やさない。

graph、閉包規則またはEvidenceの欠落・stale・競合、global invariant、横断Policy、未解決循環、
Verification ProfileまたはDecision Authorityの要求により局所scopeを安全に確定できない場合は、
通常sliceへ暗黙に材料を追加しない。`expanded_scope`、別の`full_consistency` review、Evidence
closureを保つ分割、またはHuman escalationへrouteする。scope拡大は起点、理由、判断主体、追加材料、
拡大前後のContext identityと量、機密性、終了条件をProvenanceへ保存する。budget超過を理由に
必須材料を黙って切り捨てず、安全な入力を確定できなければRunを開始しない。

#### 6.3.2 Evidence抽出、消費、Assurance

Evidence Extraction Contract、Evidence Consumption Closure、Assurance Obligation Matrix、Validator
Assurance Profile、Review Quality Contractは第7 Planではなく、6 Plan viewを横断するcompile成果とする。
Compilerは各成果を元Contract obligationへ逆引きし、欠落を`not_compilable`にする。Context Runtimeは
抽出と材料十分性、Semantic Traceは消費関係、Workflowはenforcementとpermit効果、Verificationは
validator保証とpost-write verificationを、それぞれの既存state ownerとして扱う。
CompilerとTraceは前節の7 sub-obligation IDを被覆mapの安定キーとし、まとめ記述や配列位置を
obligation identityとして扱わない。

### 6.4 Decision AuthorityとDelegation Authorization

判断の内容と、その判断を行う権限を分離する。すべての判断はDecision Recordとして保存し、
`authority_mode: human | delegated_ai`を持つ。`delegated_ai`の場合は、Humanが発行した有効な
Delegation AuthorizationのidentityとDigestへ必ず束縛する。

Delegation Authorizationは少なくとも次を固定する。

- authorization ID、version、status、発行者、発行日時、有効期間
- 委譲するdecision classと対象となるRequirement、Contract、risk、成果物の範囲
- 許可するmodel、capability、Tool、permission、side effectの上限
- 能力判定に使ったEvaluation Profile、trial、Outcome Label、metric、限界とEvidence Digest
- 判断時に必要な入力、独立review、信頼度または不確実性、追加検証
- scope mismatch、期限切れ、能力低下、競合、stale、異常時の停止とHuman escalation
- 取消し、再評価、後継authorization、影響閉包と既存Decision Recordの再確認方法

AIはDelegation Authorizationの発行、対象拡張、期限延長、取消し解除を行えない。Compilerと
WorkflowはContractのAllowed Capabilities、Provenance Obligations、Escalation Policyに加えて
authorizationのscope、status、期間、capability identityを照合する。一致しない場合はHuman
Interaction Planへ戻し、判断または完了permitを生成しない。

Humanによる後続判断は、委譲AIの判断を上書きして消すのではなく、`supersedes`または
`revokes`関係を持つ新しいDecision Recordとする。能力Evidenceの誤りや劣化が判明した場合は、
authorizationを停止し、その権限下の判断と下流成果を影響閉包に従ってstaleにする。

初期開発ではDelegation Authorizationを発行せず、全decision classをHuman modeで実行する。
ただし、後から委譲の妥当性を評価できるよう、Decision RecordとProvenanceには判断class、主体、
入力Evidence、理由、結果、後続Outcomeを保存できるidentityとrelationを初めから確保する。

### 6.5 Terminology Control

人が意味を理解する正本候補を`docs/current/reviewcompass3-glossary-current.md`とする。用語集の
entryは日本語表示名、canonical token、定義、類似語との差、status、aliasまたは後継語、
適用範囲を持てるものとする。初期版はMarkdownで運用し、専用databaseや汎用ontologyを作らない。

state、relation、decision classなど、実行時に閉じた値を必要とする語は対応schemaまたはPolicyを
機械正本とし、用語集を説明上の正本とする。両方を`term_id`またはcanonical tokenで結び、差異を
検出した場合はどちらかへ自動追従させず`terminology_inconsistent`として停止する。自由文の全語を
辞書照合するのではなく、まずschema field、enum、成果物種別、lifecycle state、relation、明示的な
term referenceを決定的に検査する。

用語の追加、意味変更、alias、retirementは、旧version、変更理由、決定者、影響閉包、更新した
schemaまたは文書をProvenanceへ記録する。過去Evidenceの語をin-placeで置換せず、読み替え関係で
現行語へ接続する。

### 6.6 過剰実装を避ける共通境界

- 6 Planは一つのbundle内のtyped viewとし、独立artifactとstate machineを作らない。
- Challengeは三Verdictの意味を分け、Run、reviewer、round、Human gateはriskに応じて構成する。
- 全symbolを機械Indexへ収録し、LedgerのHuman確認は共有、high-risk、重複、retired、影響範囲へ絞る。
- Provenanceは必須・耐久、運用、診断・raw、派生物を分け、保存とretentionを一律にしない。

独立したauthority、lifecycle、security／retention、failure recoveryまたは実測scaleの根拠がない限り、
別component、別service、別approvalへ分割しない。理由、過剰化条件、分離を認める条件は
[Task Contract設計の過剰実装を避ける境界に関するメモ](../design/2026-08-03-overdesign-boundaries-memo.md)
を参照する。

## 7. Review、Work、TDD lifecycle

### 7.1 Contract definition

```text
draft → challenged → approved
  ├─ revision_required
  ├─ rejected
  ├─ stale
  └─ superseded
```

Definition Challengeはsource Requirements、Architecture Policy、risk catalog、隣接Contractを
固定材料とし、責務欠落、狭すぎる境界、禁止side effect、依存、cross-contract責務を検査する。
Contract分割は、一つの責任、独立して観測可能な受入、必要なretry／termination境界、side effectの
所有、再利用または追跡価値を基準とする。独立して受理、復旧または追跡できない内部手順を、
Contract数を増やすためだけに分割しない。

Definition Challenge、Conformance、Final ChallengeはVerdictの意味、基準、failure routeとして分離するが、
常に別Runを要求しない。low riskでは一つのRunから別identityのVerdictを生成でき、mediumは影響に応じて
独立させ、highまたは外部・不可逆side effectでは必要な独立reviewerとHuman gateを要求する。同じ
Finding候補と固定材料をVerdictごとに複製せず、stale後は影響を受けたVerdictだけを再実行する。

### 7.2 Delivery Work Item

```text
queued → active → red → implementation_ready → green → verified → accepted
```

任意の進行状態から、blocking依存、cycle、upstream inconsistency、pause、cancel、scope exitへ
移れる。`accepted | cancelled | replaced`を耐久終端とし、旧Work Itemをin-placeで書き換えない。

`implementation_ready`はred後に固定source tree、Source Symbol Index、Reusable Routine Ledger、
実codeを照合し、必要なDecision Recordが確定したgreen実装permitである。初期開発ではこの
判断をHumanが行う。Index stale、権限未確認、理由なし分離、retired routine無断復活では
進めない。

### 7.3 TDD成果物

一cycleで次を結ぶ。

- Contract、source Requirements、challenge、Plan bundle
- Acceptance Test、Evidence Test、red Evidence
- Source Symbol Index、Ledger、Discovery Record
- LLM proposal、Decision Record、必要なDelegation Authorization、retired routine verdict
- Design Decision、Implementation change
- green Evidence、refactor、同一Testでのgreen再確認
- risk-based verification、Conformance、Final Challenge
- origin、continuation、prior Work Item
- Upstream Finding、Revision Proposal、Dependency、cycle、termination
- acceptance Decision Record、Operational Provenance verdict

RequirementまたはContract期待が変わる場合は新Contractと新Test versionへ移る。同じContractの
実装都合でTest期待を弱めない。green後のrefactorは独立stageにせず、同一ContractとTestを
維持する版付きactivityとeventにする。

### 7.4 risk-based verification

TDDの内側の反復と、`verified`、Integration Verdict、releaseの関門を分ける。

- `low`：反復と`verified`でaffected testを実行する
- `medium`：反復と`verified`でaffected testと必要なcross-contract testを実行し、次のintegration
  checkpointで全testを実行する
- `high`：反復中はaffected testと対象安全testを実行し、固定Source Snapshotの`verified`前に全test、
  fault injection相当、代表data、独立reviewを実行する

release候補はriskにかかわらず、固定Source Snapshotに対する全testと必要なdeployment／migration
verificationを通す。mediumの全testを各実装反復へ一律に要求せず、highも全test前の局所反復を許すが、
必要な関門の全testを省略しない。

保存、削除、機微情報、権限、状態遷移、外部送信、migration、uninstall、Provenance完全性は
原則highとする。Profileは`change_semantics`、`acceptance_truth_changed`、`state_effect`、
risk、side effectから選ぶ。文書、調査、Contract候補には形式的red-greenを一律強制せず、
統合対象commitは原則greenとする。赤testだけの別commitは必須にしない。

#### 7.4.1 非機能義務の接続

性能、規模、信頼性、費用、互換性、security・privacy、maintainabilityに関する必須義務は、
RequirementまたはArchitecture Policyをauthorityとし、適用条件、workload／fixture、環境、metric、
thresholdまたはinvariant、failure verdict、必要Evidenceを持つVerification Profileへ接続する。
必須義務に対するProfileを生成できなければ`not_compilable`とし、Test内の基準だけで上流義務を
置き換えない。

初期sliceでは安全、data保護、復旧、compatibilityの必須invariantを優先する。性能、規模、費用は
測定方法を先に固定し、Work 8のbaseline取得後にHumanが根拠のある閾値をRequirementまたはPolicyへ
確定する。shared／distributed固有の品質義務は対応deployment profileまでdeferする。詳細な理由、
品質属性別の扱い、最小構造は
[非機能要件とVerification Profileの接続に関する検討メモ](../design/2026-08-03-non-functional-requirements-verification-profile-memo.md)
を参照する。

#### 7.4.2 大規模codebaseの増分処理

affected-test selectionはSource Symbol Index、意味graph、Test参照、Contract／Requirement関係から
選択理由と残余riskを生成する。graph、Index、Test参照が欠落、staleまたは競合して安全な影響閉包を
作れない場合は、選択範囲を拡大して全testを実行するか、Verificationを停止する。

Source Symbol Index、意味graph、affected-test map、評価projectionは変更file／symbolと影響閉包を使って
増分更新する。定期checkpointでは固定sourceから全再生成した結果と比較し、driftを検出する。Test結果の
再利用はTest、依存閉包、tool、environment、Profileが同一で、変更集合の非影響を証明できる場合だけに
限定する。content Digest一致だけで異なる条件のEvidenceを再利用しない。

integration checkpoint、定期監査、releaseで全testを実行し、選択器の見逃しを測定する。見逃しを
検出した場合は選択器、影響graph、再利用Evidenceと下流Verdictをstaleにする。実行時間、cache、Index、
log、Provenanceのbudget、quota、retention、compactionをProfileで定め、budget超過時は必須Testを黙って
省略せず、Work Item分割、checkpointへのroute、または停止を選ぶ。

詳細な問題認識と初期設計を軽量化する境界は
[大規模・複雑なソフトウェア開発を前提とした設計評価](../design/2026-08-03-large-complex-software-design-assessment.md)
を参照する。

## 8. 開発入口、上流改定、依存、中止

### 8.1 routing

```text
work_origin: new_development | maintenance
continuation_mode: fresh | reopen
```

4組合せを共通Deliveryへrouteする。maintenanceはbaseline、invariant、regression、compatibility、
migration、rollbackを追加入力にする。義務変更時はRequirementsへ戻る。reopenはprior identityと
理由を持つ新Work Item、RunまたはContract versionであり、旧成果を保持する。

### 8.2 Upstream Revision

不整合はUpstream Inconsistency Findingとして、検出元、競合、Evidence、代替、risk、cost、
checkpointを固定する。変更分類は次を使う。

- `change_semantics`: `editorial | evidence_only | implementation_only | contract_semantic |
  requirement_semantic | scope_semantic`
- `acceptance_truth_changed`: booleanと理由
- `state_effect`: `no_state_change | advances_workflow | changes_contract |
  changes_requirement | changes_scope | external_or_irreversible`

変更が必要な最下位層をImplementation、Design Decision、Task Contract、Requirement、Feature、
Intentの順に選ぶ。意味不変訂正は新Contractを要求しない。意味変更は軽微修正を停止し、
prior／proposed identity、影響閉包、stale、Test migration、Human authorityを持つRevision
Proposalと新versionのredへ移る。

### 8.3 dependencyとcycle

境界外問題はDependency Discovery Recordへ切り出す。blocking依存は親を停止し、依存辺追加ごとに
循環を検出し、自己循環または複数node循環を`blocked_by_cycle`にする。依存graphは未解決blocking辺を
持たない実行可能leafの集合を提供し、その集合から実際に開始するWork Itemは次節のscheduler
policyが選ぶ。

解決候補は誤辺除去、owner・方向訂正、共通前提Contract、版付きinterfaceまたはstub、phase
分割、不可分Contract統合、上流再設計、defer、cancelとする。解消後も親を直接再開せず、
Contract、Plan、Context、checkpointのfreshnessを検査する。

### 8.4 scheduler policyと段階的な並行作業

Workflowは単一active leafをstate modelの不変条件にせず、版付きscheduler policyとして扱う。

```text
single_active_leaf
  → bounded_parallel
```

初期releaseと最初のvertical sliceは`single_active_leaf`を使う。これは実行可能leafから一件だけを
選ぶ安全な初期policyである。`bounded_parallel`は、実行可能leafのうちconflict domainが互いに
重ならない集合だけを、設定した上限内で選ぶ。独立性を証明できない候補は競合なしと推測せず、
直列へfallbackする。

conflict domainは少なくともprojectとBinding、固定source snapshotまたはbase identity、Requirement、
Contract、file、symbol、state owner、write target、外部または不可逆side effectを対象とする。
各並行Work Itemはowner、lease（期限付き実行所有権）、期限、scheduler decision、候補集合、採否理由、固定source identityを
持つ。lease切れだけを根拠にside effectを伴うWork Itemを別workerへ再割当てせず、durable checkpoint、
idempotency key、実行済みside effectを照合する。

並行Work Itemの局所greenまたはacceptedだけでは統合完了にしない。固定した各成果、統合対象base、
merge結果をintegration checkpointへ束縛し、競合解決、stale閉包、必要なTest、Stage FのIntegration
Verdictを通す。base、conflict domain、共有stateまたは成果が変われば、影響を受ける並行可能性判断、
Test Evidence、Verdictをstaleにする。

設計上のidentity、state境界、negative fixture、観測eventは初期から用意するが、実並行は直列E2E、
durable再開、stale、二つ以上のContractのIntegrationがgreenになった後に導入する。Work 8でshadow
schedulerを評価し、開始条件を満たす場合だけ、`local_integrated`、単一project、`max_parallel: 2`、
low risk、相互に素なconflict domain、Human判断へ限定したPilotを行う。効果または安全性を確認できない
場合は`single_active_leaf`を維持し、初期releaseをblockしない。Pilotが成功しても、
`bounded_parallel`を初期releaseの既定policyへ自動昇格させず、正式昇格は別のHuman判断とする。

### 8.5 controlled termination

- `pause`：再開予定。最後の有効成果と再開条件を保存する。
- `cancel`：現在のWork Itemを終了する。必須Requirementは未充足のまま残す。
- `close-scope`：Requirementまたはrelease scopeの新versionをDecision Recordで判断する。初期は
  Humanが行い、後続ではこのdecision classを明示した有効なauthorizationがある場合だけ委譲する。

理由、Evidence、代替、部分side effect、cleanup、rollback、未処理、移管先、決定者がない終了は
完了にしない。

## 9. 改善候補とIssue Resolution Path

### 9.1 改善候補の受付とroute

自己適用中に得た問題、改善案、新機能案は、改善候補（`improvement_candidate`）として、
発生元Work、固定source、Evidenceを記録してから扱う。現行のPlan、Task Contract、Testまたは
受入基準を先に変更しない。Implementation、Test／oracle、Task Contract、Requirement、Intent、
外部blocker、process改善、product ideaへ分類し、current Work、Upstream Revision、Dependency、
Issue Resolution、checkpoint queue、defer、rejectまたはduplicateへrouteする。

safety、authority、Acceptanceの真偽、必須Provenance、source／Test／Verdict identity、不可逆または
外部side effectへ影響する候補では現行Workを`pause_and_triage`する。それ以外はcheckpointまで
継続できる。機械またはAIは必須fieldの検査、分類とrouteの提案までとし、Plan、Requirement、
Task Contract、Test、permitを自動変更しない。上流改定、Issue昇格、risk受容、再開はHumanが判断し、
採用候補はconsumerとOutcomeへ接続されるまでclosedにしない。

初期は実行チェックリストによる手作業規律として運用し、Work 8で評価する。製品schema、正式state、
permit連携、自動Plan編集は14.4の後続判断まで導入しない。詳細な分類と決定表は
`docs/design/2026-08-03-self-application-improvement-routing-memo.md`を参照する。

### 9.2 Issue Resolution Path

Issue処理を第8 stageまたは独立engineにしない。以下は手作業Pilotで検証する概念modelであり、
初期製品の確定schemaまたは自動state machineではない。

```text
Problem / Finding / Incident
  → Issue Record
  → Triage and Disposition
  → Issue Resolution Plan
  → Plan Challenge
  → upstream layer / Task Contract Portfolio / direct Work Item
  → compiled Plan bundle
  → Task Contract TDD Delivery
  → Resolution Verdict
```

Issueは問題とEvidence、Resolution Planは意味的対処と作業分解、compiled Plan bundleはRuntime
設定を所有する。Planにはscope、non-scope、禁止事項、作業項目、依存、expected outcome、
oracle、検証、risk、deployment、rollbackを保持する。Plan Challengeはschema・参照だけでなく、
粒度、実現可能性、TDD closure、禁止事項移送を独立reviewする。固定材料またはPlanのDigestが
変われば旧合格をstaleにし、blocking FindingがあるPlanからWork Itemを開始しない。

初期はWork 8の手作業Pilotとする。Pilot前に製品schema、正式Requirement、Workflow permitを
確定しない。Issue管理UI、外部tracker同期、汎用project managementも先行実装しない。

## 10. Provenanceと評価

### 10.1 Operational Provenance

全event共通envelopeはevent ID、type、schema、time、actor、該当するproject／Work／Run、input／output
identityとDigest、保存分類、previous event、型付きrelationへ限定する。Requirement、Contract、
obligation、state、decision、change semantics、verification、duration、resource、costなどは必要なevent
typeのpayloadへ置き、無関係なfieldを全eventへ要求しない。scheduler eventはpolicy、候補集合、owner、
lease、固定source identity、conflict domain、並行採否と理由、fallback、integration checkpointを持つ。
判断eventはdecision class、authority mode、authorization identityとDigest、capability identity、
能力Evidence、scope照合結果、有効期間、escalationまたはrevocationを保持する。

append順序と意味依存を分け、`derived_from | compiled_from | satisfies | evidences |
supersedes | invalidates | evaluates | decided_by | requires | blocks | discovered_during |
related_to | resumes_from | terminated_by | matches | reuses | extends | merges | splits_from |
retires | authorized_by | delegated_under | revoked_by`などの閉じた関係を使う。必須eventまたは
関係欠落時は成果を削除せず
`provenance_incomplete`として`verified`と`accepted`を拒否する。

抽出、候補分類、消費閉包、Assurance matrixのcompileとenforcement、validator assurance、
post-write verification、session source availabilityと復元検証も型付きeventとして保存する。

Capture Profileは必須・耐久event、運用event、診断・raw data、再生成可能な派生物を分ける。Decision、
authority、permit、state、external／不可逆side effect、Verification、acceptance、stale、termination、
integration、releaseはsamplingせず、欠落時に`verified`または`accepted`を拒否する。retry、checkpoint、
lease、cacheなどの運用eventはriskに応じてbatch化でき、debug log、raw response、session raw、性能sampleは
quota、rotation、access、期限付きretentionを適用する。query index、metric、graph cacheなどの派生物は
一次eventから再生成可能とし、同じ保存義務を課さない。

文書revisionはmanifestのDigestだけで再構築可能とみなさない。recordと全manifest artifactを
同一のimmutable snapshotへ固定し、そのsnapshotから全Digestを再検証してから後継revisionを作る。
commit前の最新版は`content-present-pending-git-commit`として扱う。

#### 10.1.1 現在位置プロジェクション（`current_work_projection`）

全体計画上の位置、active Work、TDD状態、次の実行可能作業、blocker／cycle、Human判断待ち、stale／
再検証を、固定Plan、Portfolio、Work Item、Dependency、Decision、Provenance、Source Snapshot、Test
Evidenceから決定的に導出する。現在位置を別のauthorityとして手編集・保存せず、一つのstructured
projectionから初期textと後続UIを生成する。入力identity、Digest、生成時刻、freshnessを表示する。

必要入力の欠落は推測で埋めず不完全であることを、競合は不整合であることを表示して詳細を示す。
表示器だけのfailureは有効な成果を無効にしないが、authority状態の欠落によりWorkflow permitを
導出できない場合は既存規則どおりfail-closedにする。初期項目と段階導入は
[現在位置を把握するCurrent Work Projectionの検討メモ](../design/2026-08-03-current-work-projection-memo.md)
を参照する。

### 10.2 Evaluation

Operational Provenance、Evaluation Observation、Outcome Labelを分離する。Evaluation Profileは
仮説、必要観測、baseline、比較条件、trial、metric、欠測、privacy、retentionを持つ。
metricは一次eventを変更せず再計算し、過去projectionを上書きしない。任意観測の欠測は業務
成果を無効にせず`partially_evaluable | not_evaluable`とする。

初期metricはEvidence Coverage、source universeのbyte／token、変更単位数、影響閉包単位数、
review payloadのbyte／token、selection mode、scope拡大率と理由、Finding Precision／Recall、責務外率、lead time、
再作業、Human介入、Tool・token・費用、stale、dependency、termination、reuse判断、Issue
Resolution、Provenance完全性を対象とする。Precision／RecallはOutcome Labelがある場合だけ
計算する。将来の委譲判断には、decision class別の正答またはOutcome Label、Human override、
escalation、scope違反、見逃し、誤accept、誤complete、能力劣化を追加し、対象業務とriskを
混ぜずに比較する。

横断品質について、material adequacy、必須source消費率、未消費Finding、
`insufficient_evidence`、`out_of_level`、validator既知違反検出率、正常fixture誤停止率、
mutation生存数、post-write再検出を追加する。

### 10.3 実装文書projection：deferred

accepted Task ContractのProvenance、Test、Design Decision、Implementation、Source Symbol
Indexから機械可読As-Built Recordと人間向け文書、Trace Matrix、変更履歴、drift reportを
再生成する。RequirementsとTask Contractは規範正本のままとし、意味変更候補はUpstream
Revisionへ渡す。固定sourceとTestの逆照合で未帰属実装も検出する。

本能力は初期Work 1〜8、最初のTask Contract、初期vertical slice、初期releaseへ入れない。
初期開発は将来のprojectionに必要なidentity、relation、Digestを保存するだけとする。

## 11. Deploymentと配置

Deploymentは後処理ではなく、state owner、実行権限、data境界、障害復旧、更新時の自己検証を
決める設計問題として扱う。論理component境界と物理process、container、hostを分け、特定技術を
採用する前にprofileごとの責務と失敗条件を固定する。

### 11.1 論理rootとManifest

開発checkout、installed code、target project、runtime data、state、log、cache、sensitive data、
evaluation storeを分離する。

```text
CODE_ROOT
CONFIG_ROOT
PROJECT_ROOT
DATA_ROOT
STATE_ROOT
LOG_ROOT
CACHE_ROOT
SENSITIVE_ROOT
EVALUATION_ROOT
```

`PROJECT_ROOT`には共有・version管理するContract、Portfolio、Policy、Requirement map、Design
Decision、Reusable Routine Ledger、verified artifactを置ける。raw response、生session、secret、
lock、checkpoint、cache、端末固有絶対path、未検査機微情報は置かない。

`DATA_ROOT`にはProvenance、Run、Context、compiled Plan、Source Symbol Index、Discovery Record、
将来の未検証As-Built projectionを置く。`SENSITIVE_ROOT`を通常dataと分離し、Evaluationは
Observation、Label、projection、Ledgerを専用rootへ置く。

Deployment Manifestはinstalled code、supported platform、logical root、Project Binding、
Integration Binding、owned resource、migration、permission、confidentiality、retentionを持つ。
解決優先順位は明示CLI、versioned user setting、許可環境変数、OS標準配置とする。

`project_id`はProject Manifestの安定IDとし、内容Digest、repository root、checkoutごとの
`binding_id`から分離する。同一projectの複数checkoutとproject移動はBindingで扱う。Codex、
Claude、IDEとの関係は隣接配置でなくIntegration Manifestのadapter、source root、command、
read／write root、capability、permission、ownerで表す。

installはpreflight、staging、検証、原子的切替、hook登録の順、updateはmigrationとrollbackを
持つ。uninstallはowned resourceだけを削除し、project成果、Provenance、Evaluation、利用者data、
sensitive dataを既定で保持する。data削除は別の明示操作とretention policyで行う。

### 11.2 deployment profile

```text
local_integrated
  → shared_runtime
  → distributed_hybrid
```

初期releaseは`local_integrated`だけを対象とする。同一machine、単一利用者、一括install／起動を
許すが、Integration Client、Control Plane、Execution Plane、project、runtime data、sensitive
dataは論理的に分け、structured I/Oを通す。単一processか分離processか、local IPCかHTTPか、
file storeかdatabaseかは、初期E2Eを満たす最小Design Decisionで選びRequirementsへ固定しない。

`shared_runtime`は共有Control Planeとproject側Local Execution Agentで構成する。local profileの
実測後、認証、remote threat model、permission、data locality、offline、通信障害、retry、
revocationのRequirementsとnegative testを別Task Contractで確定してから着手する。

`distributed_hybrid`は複数Execution Worker、GPU、HPCまたは外部serviceへ実行を分散するprofileで
ある。scheduler、重複実行、tenant、scale、costに関する実測された必要性がない段階では作らない。

### 11.3 Control PlaneとExecution Plane

Control PlaneはTask Contract、compiled Plan、Workflow state、Policy、permit、Decision、
Provenanceを所有する。Execution Planeは固定Planとpermitに従ってLLM、Tool、command、testを
実行するが、Contract本文やaccepted stateを直接変更しない。

Execution Workerはauthorityを持つ唯一のstateをprocess内だけに保持しない。Attempt、side effect、
output capture、checkpointをdurable eventへ結び、crash後は同じidentityを照合して重複side effect
なしに再開する。shared profileのControl Planeはlocal repositoryへ包括accessせず、Local Execution
AgentがProject Bindingと期限付きallowlistの範囲だけを実行する。

### 11.4 配布・更新単位

- Runtime Core：Compiler、Workflow、state、Provenanceのcodeとschema
- Integration Client：CLI、IDE hook、開発appとの入口
- Capability Adapter：LLM、Tool、command、test等の検証済み実行adapter
- Project Artifacts：Task Contract、Portfolio、Policy、Requirement map、Prompt、Design Decision

Project ArtifactsはRuntime Coreの再deployなしに追加・更新できる。一方、実行codeはproject artifactへ
混在させず、Capability Adapterとしてcode verification、version固定、permission review、rollbackを
経る。元検討のTask Package／Task Registryはこの二分へ置換し、任意codeをloadするplugin systemや
汎用Task orchestrationは初期範囲へ入れない。

### 11.5 stable／development bootstrap

ReviewCompass3自身の開発では、確認済みstable deploymentとdevelopment candidateを別のcode、
Manifest、state、data rootへ置く。stableがcandidate sourceとartifactをreviewし、candidateを自分自身の
release可否を決める唯一のoracleにしない。

update candidateはstaging rootへ配置し、旧stableからmigration dry-run、E2E、Provenance、rollbackを
確認してからstable bindingを原子的に切り替える。切替後の検証失敗時は旧stableへ戻す。

## 12. 移行Work

### Work 1：方針と固定入力

外部source、前身commit、構造化baseline、変更判断、Digest、適用範囲、非目標を固定する。
旧第5段候補を上書きせず、Task Contract差分の再開理由を記録する。
Evidence Extraction Contractで探索と分類を固定し、必須sourceと採用FindingのConsumption Closureを
確認する。ReviewCompass2のfreeze原因と実装済みsession captureを規範ではなく経験Evidenceとして扱う。

### Work 1A：配置baseline

bootstrap成果を保存する前に、`CODE_ROOT`、`CONFIG_ROOT`、`PROJECT_ROOT`、`DATA_ROOT`、
`STATE_ROOT`、`LOG_ROOT`、`CACHE_ROOT`、`SENSITIVE_ROOT`、`EVALUATION_ROOT`の意味と解決規則を
固定する。Git管理対象とproject外data、相対参照の基準、Project Manifest、Project Binding、
stable／development、所有・retention・削除、path overrideの優先順位をLayout Baseline Recordへ
保存する。

空の配置fixtureで、別checkoutまたはproject移動後も相対参照、Manifest、Binding、文書linkが解決し、
project内へ端末固有絶対pathが保存されないことを確認する。baseline後のmanaged path変更は通常編集で
行わず、影響閉包、link検査、rollbackを持つmigrationとして扱う。

### Work 1B：Session Log Bootstrap

Work 1Aの保存境界を使い、Work 2以降の議論、判断、調査、変更からSession Evidenceを残せる最小記録
基盤を準備する。取込み対象と許可主体、session ID、source identity、開始・取得時刻、capture deadline、
content Digest、完全性、confidentiality、access、retention、mutation、source availabilityを固定する。

raw sessionは既定で`SENSITIVE_ROOT`へ保存し、伏字化派生物、要約、索引を別identityとaccessで
`DATA_ROOT`へ置く。追記と非追記変更を区別し、rawから派生物を再生成するrestore fixtureを確認する。
sourceへアクセスできない、期限切れ、完全取得できない場合は`source_missing | source_expired |
non_reconstructable`を記録し、正常な空sessionとして扱わない。

このbootstrapは開発Evidenceを失わないための最小capture profileであり、Session Records製品機能の
完成を意味しない。外部送信、許可範囲外取込み、無期限retentionを導入せず、後続の正式実装は別の
Task Contractとnegative testを必要とする。

bootstrap前から、session終了時の実施報告照合（`execution_claim_verification`）を手作業で行う。
後続状態を変える報告を実施、結果、判断、提案、未実施へ分け、実施・結果・判断Claimをpath、diff、
Digest、command結果、commit SHA、receiptまたはDecisionと、再確認した事後状態へ接続する。
EvidenceがないClaimは`reported_unverified`、報告と事後状態が競合する場合は
`report_execution_mismatch`とし、完了、checkbox、projectionへ使用しない。Session Log Bootstrapは
この記録を後から復元可能にするが、会話上の成功報告だけを操作完了のEvidenceへ昇格しない。

同時に、Work開始／完了、pause／resume、blocker発生／解消、Human判断要求／決定、upstream revision、
stale／再検証、cancel／defer、session開始／終了の最小recordから、現在位置を一つのtextへ導出する
bootstrap Current Work Projectionを準備する。手編集する`STATUS.md`、製品schema、WebUI、常駐serviceを
作らず、Work 5A後に正式なTask Contract／Workflow／Provenance recordへ入力を写像する。

### Work 2：Intent統合

製品Intentから開発方法を分離し、Task Contract、二層review、最小権限、stale、配置非依存、
評価可能性、再利用品質、Issue→Plan原則を統合する。本文書と対になるIntent統合最新版を
Human判断候補にする。AIへの判断委譲は、能力確認後の限定的な選択肢として扱い、委譲の設定と
取消しをHuman authorityとして残す。ReviewCompass2の用語統制を現行概念へ適合させた統合用語集を
別文書として作り、Intentと計画から参照する。

### Work 3：Requirements差分

追加13要件と既存37要件の順逆被覆、owner、interface、停止、復旧、受入、対象外を確定する。
`REQ-WORKFLOW-010`と`011`は手作業Pilot後の候補、`REQ-CONTRACT-008`は後続開発とする。
`REQ-WORKFLOW-007`は単一active leafを初期scheduler policyとして維持し、conflict domain、owner／
lease、並行性判断のstale、integration checkpoint、安全な直列fallbackを同じownerの後継versionへ
追加する。bounded parallelの実行能力は初期sliceの受入条件にしない。
Source Snapshot、Change Set、local／CI Verification Run、Build Artifactを論理的に分離し、Test、review、
Decision、commit、releaseの対象一致とstaleを扱うRequirement差分を確定する。特定Git hostingまたは
CI providerの操作機能は初期要件へ入れない。
既存RequirementとArchitecture Policyから非機能義務、適用範囲、failure consequenceを抽出し、
初期必須、実測後に閾値確定、deployment profileまでdeferの三つへ分類する。
判断委譲用Requirements差分は、能力Evidenceを得た後の独立Workとし、このWorkの要件数へ
含めない。用語統制のRuntime強制も、手作業運用で具体的な不足を確認した後の独立差分とする。

### Inter-work：Work 3完了後の追加correctiveと早期Pilot

このthreadで当初順序外に追加した作業を、Work 4開始前の一時的なinter-work列として扱う。変更理由、
対象一覧、完了境界の正本は
`records/development/2026-08-04-thread-added-work-plan-checklist-reconciliation-v1.md`とする。

| work | state | 実施範囲 | 未完了境界 |
|---|---|---|---|
| Session transcript eventual preservation | `verified / completed` | Codex exec／rollout／Claudeの3 source kind adapter、manual collector、durable cursor、reconcile、現在のCodex Desktop taskだけの限定実ログcapture | background automation、過去Codex／Claude log capture、長期retention、削除、暗号化、backup |
| Commit／handoff stability | `verified / completed` | commit安定TODO、post-commit read-only照合、完了済み・未コミット時の次作業停止Pilot | 自動commit、push、hook、履歴書換え |
| Deployment／Project Artifact boundary | `approved_effective / bootstrap_completed` | Layout Baseline v2、Project Manifest v2、移動させない`.reviewcompass/workflow/` root | Deployment Manifest、package builder、原子的切替、rollback、durable Project Binding |
| ReviewCompass Issue Resolution early Pilot | `approved / bootstrap_in_progress` | ReviewCompass2 Issue→Plan経路の継承、TODO routing修正案、Project Artifact上位root | Candidate／Triage Decision shape、最初の手作業record、Issue／Plan実record |

Issue Resolution早期Pilotは、Improvement CandidateとHuman Triage Decisionのidentity、field、命名、version、
Digest、参照規則を固定し、最初の手作業recordで経路を確認するところまでを前倒し範囲とする。製品schema、
正式state machine、Workflow permit、自動Plan編集、Issue Resolution automation、Work 8の評価は前倒ししない。

TODOの詳細な手戻り候補を恒久保存する経路はIssue Resolution Pilotへ接続するが、TODO自体はactive IDの
projectionに限定する。Pilot shape確定前に手作業でIssue fileを置かない。限定Pilotを終えたら、当初順序の
Work 4へ戻る。Layoutのbootstrap完了をWork 7A／7B完了、session保全corrective完了をSession Records製品機能
完了として扱わない。

### Work 4：Design差分と最初のslice選定

Contract、Portfolio、Compiler、Policy、Plan、state、interface、Provenance、Evaluation、Deployment、
Integration、upstream revision、dependency、termination、reuseを設計する。Issue Resolutionは
Work 8の手作業Pilot用の暫定owner、routing、記録項目に限定し、製品schema、正式state、permitは
Pilot後のDeferred Workへ送る。
`new_development / fresh`、`maintenance / reopen`、上流改定と依存／中止、配置lifecycle、条件付き
並行を代表シナリオとし、Requirementからaccepted artifactまでの接続を設計とE2E fixtureで確認する。
独立Feature、lane、schemaまたはgateは追加しない。確認観点と採否境界は

### 14.2 AIへの判断委譲

初期releaseではすべての採否、完了、Stage、release判断をHuman modeで行い、判断委譲は有効に
しない。次をすべて満たした後、対象を一つの低riskなdecision classに限定した別Task Contract
として、Humanが試行開始を判断する。

- 同じdecision class、対象業務、risk、入力条件で十分な件数のHuman判断と後続Outcomeがある
- 能力基準、誤判断の許容上限、停止基準、欠測時の扱いがEvaluation Profileとして固定される
- Requirements差分、threat model、negative Acceptance Test、rollbackが承認される
- Delegation Authorizationの発行、scope照合、期限、停止、取消し、stale化がE2Eで検証される
- 判断主体、根拠、authority、結果をProvenanceから再構成できる
- 誤判断時の影響が限定的かつ回復可能で、外部送信、不可逆操作、機密情報の権限変更を含まない

最初の試行はshadow modeでAI判断とHuman判断を独立に記録し、AI判断を業務状態へ反映しない。
基準を満たした場合だけ、明示した期間と件数に限るsupervised delegationへ進む。さらに継続的な
評価で能力が維持された場合だけ、Humanの事前確認を省くbounded delegationを検討する。

```text
human_only
  → shadow_evaluation
  → supervised_delegation
  → bounded_delegation
```

各遷移は新しいDelegation AuthorizationとHuman判断を必要とする。自動昇格は行わない。
取消し、期限切れ、能力低下、scope違反、重大な誤判断では直ちに`human_only`へ戻し、影響を
受ける判断と成果を再確認する。対象decision classの追加は既存authorizationの拡張ではなく、
別のRequirements、Evaluation Profile、Task Contract、authorizationとして扱う。

### 14.3 shared／hybrid deployment

`shared_runtime`は、`local_integrated`のdeployment E2Eと運用Evidenceが揃い、複数利用者または
別machine配置の具体的な必要性が確認された後に別Task Contractとして扱う。最初のsliceは一つの
project、一つのControl Plane、一つのLocal Execution Agentに限定し、serverがlocal repositoryへ
直接mountする構成を避ける。

`distributed_hybrid`はshared profileの実測後も、複数worker、GPU、HPC、schedulerの必要性が残る
場合だけ検討する。汎用Task Registry、任意Domain Package、Concierge orchestrationを同時に導入
しない。

### 14.4 改善候補とIssue Resolution automation

改善候補は、Work 8の手作業Pilotで停止条件、分類、route、consumer、Outcome、誤停止、停止漏れ、
記録費用を確認した後、別Task Contractで機械化の着手を判断する。最初の候補は必須field、identity、
Digest、freshness、重複のvalidatorとroute提案に限定する。Plan、Requirement、Task Contract、Test、
permitの自動変更は別のRequirement、Human authority、negative Testなしに導入しない。

Work 8の手作業Pilotで必須field、owner、停止条件、stale条件、費用を確認した後、別Task Contractで

結線はその検証後とする。Issue管理UI、外部tracker同期、汎用project-management機能は対象外とする。

### 14.5 `bounded_parallel`の後続導入

Work 8Aの開始条件を満たさない、またはPilotで安全性・効果を確認できない場合、実並行はこの
Deferred Workへ移す。shadow schedulerのEvidence、未検出競合、直列待ち時間、stale、再検証費用を
保持し、不足しているRequirement、Design、Test、観測を別Task Contractで補う。

## 18. 開発方針

- SDDを維持し、小さなE2E vertical sliceを優先する。
- 新抽象、schema、gateは具体的なE2E不足が確認された場合に追加する。
- 初期WIPは`single_active_leaf`へ制限する。実行可能leafが複数あっても、shadow評価と安全条件を
  満たすまで実並行を許可しない。
- 後続の`bounded_parallel`は上限、conflict domain、owner／lease、固定source、直列fallback、
  Integration再検証を必須とし、独立性を確認できないWork Itemを直列化する。
- 振る舞い変更には実装前または同一変更内で有効なtestを用意する。
- riskに応じてlow、medium、highのverificationを適用する。
- 文書、調査、試作へ形式的red-greenを強制しない。
- 赤testだけのcommitを必須にせず、統合対象commitは原則greenとする。
- stableな機能だけを自己適用の必須経路にする。
- 自己適用で得た問題、改善案、新機能案は改善候補として記録し、分類、停止判定、route、
  consumerとOutcomeの確認を行う。現行の受入基準を先に変更しない。
- 機械またはAIによる改善候補の分類とrouteは提案までとし、上流改定、Issue昇格、risk受容、
  再開はHuman判断へ残す。
- 会話、TODO、checklist、最終報告の実施Claimを固定Evidenceと事後状態へ照合し、報告だけを
  完了根拠にしない。Evidence欠落は未完了、実態との競合は停止として扱う。
- stable deploymentとdevelopment candidateのcode、Manifest、state、dataを分離し、stableから
  candidateを検証する。
- Pythonは4 spaces、他言語は標準formatterを使い、一括整形を機能変更へ混在させない。
- 初期開発では、方針変更、採否、完了、外部送信、不可逆操作、意味的裁定、Stage完了を
  Human判断へ残す。
- 後続のAI判断委譲は、承認済みRequirementsとDelegation Authorizationの範囲内だけで行い、
  委譲の設定、変更、停止、取消しはHuman判断へ残す。
