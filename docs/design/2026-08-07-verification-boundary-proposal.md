## 3. 提案：三層の検証境界

### 層1「機械が保証する」——決定的に判定できるもの

同じ入力から同じ結論が出て、反例を機械で示せるもの。指紋照合、参照解決、範囲の一致、
形式検査。**この層に属するのに未実装なら、それは欠陥である**。

### 層2「機械が支援する」——完全ではないが誤りを減らせるもの

網羅は不可能だが、既知の危険や典型的な誤記を検出できるもの。**安全保証ではなく誤記検出**で
あることを、実装とrecordの両方で明示する。過信を招かないことが要件である。

### 層3「機械は保証しない」——Humanが担うもの

文章の真偽、意図の正しさ、host側の実際の権限。**機械が保証していないことを明示し、Human確認の
対象として記録する**。黙って通すのではなく、「ここは検証していない」と表示する。

## 4. 11件の割り当てと具体案

### 層1へ入れる（実装すべき欠陥）

| ID | 内容 | 実装案 |
| --- | --- | --- |
| **C-4** | `red_now`（宣言に結ばれたtestが本当に失敗するか）が一度も確認されていない | 対応表検査器に`--verify-red`経路を足し、列挙testを実際に実行して`red_now`と突き合わせる。**実行は明示指定時のみ**（既定は現行の静的検査）。実行時間は対象testに限定されるため小さい |
| **R-3** | `hits`を空にした「検索したふり」recordがgateを通る | gate時に検索を再実行し、`content_digest`の一致を確認する。決定的再生成はR-3宣言で既に固定済みであり、gateがそれを使っていないだけである |
| **C-1完全解消** | 欄からも宣言からも漏れた実在testを検出できない | 対応表に`scope`欄（`complete`＝file内の全testを対象／`partial`＝列挙分のみ、理由必須）を追加する。`complete`なら実在test全体と突き合わせ、`partial`なら理由をrecordへ残す。既存のIntake対応表は`partial`として明示する |

**C-4を最優先とする。** 関門の名が「宣言→**RED**対応表」でありながらREDを確認していないという
状態は、この開発が最も重視してきた保証の**質**に直結する。
