## 1. 構図：旧方式とRC3の写像

旧方式は行列——縦串＝機能module、横串＝要件以降のフェーズ——の**両方向にレビュー**を持っていた。
RC3のTask Contract方式は縦串（小さなE2E縦切り＋受入・完了レビュー）が強く、**横方向のレビュー
制度が不在**。全体整合は2層に分けて再導入する：

- **機械層**＝アーキテクチャ宣言＋整合検査器（依存方向・語彙単一性・配置）——登録済み候補
- **意味層**＝横串レビュー（責務重複・境界の筋・module間の要件整合）——本memoの主題

## 2. 有効性の条件と限界（批判的検討の結論）

1. **宣言は載荷必須**：機械規則部はcheckerが毎回読み、意味観点部は横串レビュー依頼の組み立てが
   digest束縛で必ず引く。使われない宣言は数日で古びる（checklist参照digestのずれ＝実害記録）。
2. **横串レビューは差分駆動・対象限定が原則**：RC1実測で45KB以下は213回中失敗1、82KB×網羅観点は
   破綻。全module一括の横串は初回分割時のみとし、以後は「変化した接続点の周辺」だけを見る。
3. **静かな意味的歪み**（構造が変わらないまま流儀がずれる劣化）は差分駆動で捕まらない——
   checkpoint時の全景見直し（見取り図＋宣言＋台帳を入力・観点限定）を補助として残す。
   これは旧方式の全面横串より弱いが、現規模（tools 177 file）では旧方式も成立しない。

## 3. 機能分割のLLM委任の評価

- 初期案の生成としては有効（標準形の提案は得意）。ただし**正しさの根拠にはならない**：
  (a) 案は標準形に寄り案件固有の力学（変更頻度・データ所有・配布境界）を読まない、
  (b) 承認時点の分割表は無負荷で、承認は弱い検証、(c) 分割の正否は事後にしか分からない。
- よって位置づけは「**LLMが提案し、人が承認する版付き仮説**。機械が実測で検証し
  （共変更・契約のmodule跨ぎ数・接続点密度＝git履歴と運用集計の型で算出可能）、人が証拠つきで
  改定する」。やり直しは失敗ではなく設計されたloop。
- RC3自身の宣言初版は**発明でなく記述**（現状をコードから機械抽出し人が直す）。発明が要るのは
  新アプリ側のみで、縦切り方式自体が早期の痛み検出という保険になる。

## 4. 流れ（合意版）

```
intent
 └→ LLM分割案 → 人が明示承認 ＝ 宣言v1（版付き仮説）
     └→ module毎の構造化要件（provides/requires・intent対応・責務語彙の欄を持つ）
         └→【横串gate（初回一括）】機械篩 → LLM意味レビュー → 人裁定
             ├─ 信号あり → 宣言v2へ改定・影響要件のみ再割当 → gate再実行
             └─ 通過 → Task Contract群（縦切りTDD）
                 ├─ 受入毎：checker＝宣言との整合（速いloop）
                 ├─ 接続点差分 → 差分駆動の横串レビュー
                 └─ 運用実測（共変更・波及）→ 宣言改定の材料（遅いloop）
```

機械篩の信号（要件recordから決定的に算出）：intent項目の被覆漏れ・責務重複の近似・
requires／provides不整合と依存の輪・1moduleへの要求集中。

## 5. 役割分担表（基本方針＝LLMは意味的分析・他は機械で決定的に）

| 工程 | LLM（意味のみ） | 機械（決定的） | 人（裁定） |
| --- | --- | --- | --- |
| intent | 言語化の支援 | — | intent確定 |
| 機能分割案 | 分割案の生成 | 宣言schemaの形式検査 | 承認＝宣言v1 |
| 構造化要件 | 要件文・責務の記述 | 要件writer（機械欄埋め・検証合格時のみ書き出し） | 要件確定 |
| 横串gate篩 | — | 被覆・重複近似・provides照合・輪・偏りの計数 | — |
| 横串レビュー | 境界の筋・意味整合の所見 | 依頼組み立て（対象・観点のdigest束縛）・判定schema検証 | — |
| gate裁定 | 裁定材料の圧縮 | 決定writerで機械記録 | やり直しか通過か |
| 契約・TDD | 契約文・テスト意図 | RED／GREEN・受入測定ブロック | 受入 |
| 速いloop | — | checker（import解析・語彙・配置） | 違反の裁定 |
| 遅いloop | 実測の意味づけ | 共変更・跨ぎ数の集計 | 宣言改定 |

検証結果：どの工程にもLLMが決定的処理を担う箇所は無い。LLMの仕事は分割案文・要件文・
レビュー所見・裁定材料圧縮の4つに閉じる。

## 6. 新設が必要な機械部品（実装対象の見取り）

1. 宣言schema＋検証器（版付き。機械規則部＋意味観点部の2部構成）
2. **要件writer**（候補writerと同型。無いと要件recordの手組みが再発する）
3. **横串篩**（宣言×要件recordからの決定的算出）
4. checker（実装段＝機械層候補の中身）
5. 境界実測（共変更・跨ぎ数＝運用集計の拡張型）

運搬（依頼record組み立て・判定検証・改善lane）は既存部品を再利用。実装の入り方は
**案A（自由文レビュー類型の運用パターン定義）から始め、効けば案B（依頼record第4類型）へ昇格**。
