ReviewCompass3の全体計画は、端的に言えば次のものです。

> AIへ仕事を依頼し、必要な材料を渡し、実行結果を検証し、人が判断し、その全過程を後から再現できる仕組みを作る。

そのために、「何をするか」「何を使ってよいか」「何を成果とするか」「どう検証するか」を小さな作業単位ごとに固定します。この小さな仕事の約束を、計画では「作業契約」と呼んでいます。

## 1. 製品全体の構成

ReviewCompass3は、おおむね次の10機能から成ります。

1. 作業契約の管理
   要求を実行可能な作業へ変換し、抜けや重複を確認する。
2. レビュー材料の準備
   対象、資料、対象外、変更影響範囲を固定する。
3. AIや外部処理の実行管理
   送信内容、承認、実行回数、未加工応答、再開を管理する。
4. レビュー結果の整理
   複数の指摘、重複、対立、人の採否を整理する。
5. 要求と成果の追跡
   要求から実装、試験、判断までを相互にたどれるようにする。
6. セッション記録
   CodexやClaudeの会話記録を保存し、伏字化した派生物へ結び付ける。
7. 作業の進行管理
   開始、停止、再開、依存関係、完了、次の作業を管理する。
8. 配置と更新
   インストール、設定、作業データ、機密データを分離し、安全に更新・解除する。
9. 評価
   新方式が従来方式より本当に安全・効率的かを実測する。
10. 改善
    失敗や改善候補を記録し、勝手に本線へ割り込ませず、適切な作業へ渡す。

## 2. 標準的な開発の流れ

計画では、すべての機能を次の7段階で進めます。

```
A. 製品の目的
   ↓
B. 機能と責任の分割
   ↓
C. 要求の確定
   ↓
D. 作業契約の編成
   ↓
E. 試験を先に作る実装
   ↓
F. 機能同士の接続確認
   ↓
G. 公開・配布できるかの評価
```

これは一方向ではありません。実装中に要求の誤りが見つかれば、必要な段階まで戻って新しい版を作ります。

## 3. 実際の移行作業

既存資産から新しい仕組みへ移る作業は、次の順序です。

### 基礎を作る

- Work 1：過去の資料、判断、基準値を固定する
- Work 1A：コード、設定、作業データ、機密データの保存場所を分ける
- Work 1B：セッションログを失わない最低限の保存経路を作る
- Work 2：製品目的を統合する
- Work 3：既存要求と追加要求を統合する

### 最初の製品経路を作る

- Work 4：全体設計と、最初に実装する小さな縦切りを選ぶ
- Work 4A：既存コードから再利用できる処理を機械的に探せるようにする
- Work 4B：実際の開発で再利用・統合方法を試す
- Work 5A：最小のレビュー作業契約を、正常系だけ通す
- Work 6A：欠落、改ざん、古い入力、部分成功などの異常系を扱う
- Work 5B：ReviewCompass3自身の小さな実装を、作業契約方式で一件試す

### 実運用に近づける

- Work 7A：別の作業場所でも動く最小配置を確認する
- Work 8：新方式と従来方式を同条件で比較する
- Work 8A：必要性が実測できた場合だけ、二作業までの並行処理を試す
- Work 7B：更新、移行、解除、巻き戻しまで確認する

### 最後に行う

- 機能同士の統合確認
- 対応環境、配布物、データ保護の確認
- 人による初回公開判断

## 5. 今回のClaude作業の位置づけ

今回進めていたものは、製品本体の次の機能ではありません。

> Codexが主担当となり、Claudeへ実装だけを任せ、別のCodexモデルがレビューするための開発支援経路

これは本来、Work 5B以降の開発を効率化するための補助経路です。確認すべきだったのは、合成リポジトリで次の一往復が成立することだけでした。

```
Claudeが試験を作る
  ↓
機械が不合格を確認する
  ↓
Claudeが実装する
  ↓
機械が合格を確認する
  ↓
独立レビューへ渡す
```

ところが実際には、途中で見つかった次の問題をその場で連続修正しました。

- Claude応答の解析方法
- 中断後の再開
- 承認票の状態管理
- 管理者領域への配置更新
- 過去版のDigest管理
- 通信切断後の部分成功処理

これらは本来、それぞれ別の異常系作業または配置作業です。確認運転の中へ押し込んだため、補助経路の確認が、実行基盤全体の再設計へ膨らみました。

## 7. 現時点での正しい停止位置

現在は次の位置で止めるのが適切です。

```
全体計画
  └─ Work 5B以降の開発支援
      └─ Claude実装委譲経路
          └─ 合成リポジトリ確認運転
              ├─ 第1ターン：完了
              ├─ 第2ターン：実装は生成、終了通信に失敗
              ├─ 独立レビュー：未実施
              └─ 段完了：未承認
```

つまり、プロジェクト全体が止まっているのではありません。補助経路の確認運転が、部分成功状態で停止しています。

次に必要なのは実装の続行ではなく、まず全体計画、完了記録、現在位置、Claude作業の所属を一致させ、本線と枝作業を再分離することです。



その通りです。先ほど示したのは「製品機能の実装計画」に偏っており、開発を支える横断的な計画を落としていました。全体像は次の構造です。

```
ReviewCompass3
├─ A. 製品本体
│  └─ Work 1～8（証拠管理、評価、外部連携、運用など）
│
├─ B. レビューの仕組み
│  ├─ レビュー依頼を機械的に組み立てる
│  ├─ 独立した担当が実装結果を確認する
│  ├─ 危険度に応じて確認量を制限する
│  └─ 合否を決める検証コード自体も再レビューする
│
├─ C. 開発コードの管理
│  ├─ 既存処理を検索してから新規実装する
│  ├─ 重複候補を機械的に抽出する
│  ├─ 共通化するか分離を維持するか判断する
│  └─ 合否を左右する重要コードを一覧管理する
│
├─ D. テストコードの整理
│  ├─ 重複する試験準備を共通化する
│  ├─ 要求と受入試験の対応を機械照合する
│  ├─ 正式な試験実行結果を正しく記録する
│  └─ 一時的な範囲確認試験を通常試験から分離する
│
├─ E. 作業状態の管理
│  ├─ セッションログ
│  ├─ TODOと現在位置
│  ├─ 改善候補と問題の振り分け
│  └─ コミットと引き継ぎ
│
└─ F. LLM協業の試行
   ├─ Codex主担当
   ├─ Claude実装担当
   └─ 別モデルによる独立レビュー
```

重要なのは、B～Eが単なる付随作業ではなく、Aのすべてを支える開発基盤だという点です。Claude連携はその中の一つの試行であって、全体計画の本線そのものではありません。

現状は次のとおりです。

- 【記録】レビュー手順と、危険度に応じて過剰なレビューを抑える規則は作成済みです。
- 【記録】合否を左右する重要な検証コード94件を特定し、高危険度19件を再レビューしました。
- 【記録】その修正はE群、A群、B群まで進みました。
- 【記録】現在位置を管理するC群は複雑化したため変更を取り消しており、5件が未解決です。実行・台帳境界のD群7件も未解決です。
- 【実測】テスト準備コードの重複整理は完了し、当時の全試験1338件は合格しています。
- 【実測】一方、現在は古い変更範囲を固定した試験が残り、通常の全試験を不安定にしています。
- 【実測】現在位置を示す計画文書とTODOも、実際の作業に追従できていません。

したがって、今回コントロールを失った直接的な原因は、未完了だった「現在位置の管理」を飛び越えてClaude連携を伸ばしたことです。しかもClaude連携の中で、送信、認証、解析、復旧、配置更新まで扱い始め、限定的な協業試験が独立した開発本線のように膨らみました。

【判断】本来の順序は次です。

1. 全体計画と現在位置を一つの正本へ戻す。
2. 未解決のC群5件・D群7件を、修正するか明示的に延期する。
3. 古い一時的な範囲確認試験を通常試験から分離する。
4. その後、Claude連携を「固定2ターンの協業試験」という限定範囲へ戻す。
5. 安定した部分だけを製品本体の開発手順へ取り込む。

Claude連携だけを止めても不十分です。レビュー、コード管理、テスト整理、現在位置管理を含む横断計画を復元する必要があります。そこまで含めて初めて、プロジェクト全体の計画になります。
