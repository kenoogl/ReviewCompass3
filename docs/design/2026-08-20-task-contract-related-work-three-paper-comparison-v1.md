## 1. 結論（要旨）

新規性は主張できる。ただし条件付き。3本のいずれも、RC3の中心主張——実行タスクの責務を
機械解釈可能な契約として宣言し、その契約から文脈取得・レビュー観点・実行環境（ハーネス＝
ツール・権限・検証などの設定一式）・人の介入点・検証計画・来歴（provenance＝情報の出所と
利用履歴）収集までを系統的に導出する——を扱っていない【実測】。一方で、周辺の個別主張
（構造化仕様の入力で品質が上がる、タスクに応じた文脈を動的に集める、副作用を検証する、
機械解釈可能な契約という概念）は、それぞれ先行論文に先取りされている【実測】。したがって、
アーキテクチャmemo §9の「個別要素は既存であり、統合的な導出関係が貢献」という守り方が
この3本に対してもそのまま有効であり、個別要素を単独の新規性として立てると潰される【推測】。

## 2. 各論文の要点とTask Contractとの重なり・違い【実測】

### 2.1 SSDE（最接近。最も注意が必要）

構造化した仕様——Gherkin（振る舞いを「前提・操作・期待結果」の形式で書く記述法）、
ドメインモデル（Umple・Ecore）、署名モデル（モデル層のAPI署名）——をLLMへの入力にすると、
自然言語だけの指示より生成品質と検証可能性が上がる、という構想論文。パイロット実験は
Python MVCの業務ロジック（コントローラ）生成で、GitHub上の3システム（Symboleoのコードを
含む）×5 LLM×反復10回を、人手作成の単体テスト合格率（TPR）で評価。0-shot・フィードバック
なしの単発生成。

- 主結果：モデル類の構造化仕様を加えると自然言語のみの基線を大きく改善。Gherkin対自然言語
  （モデル併用時）は平均TPRで6.8%劣るが、30組合せ中14で上回り、その改善平均は+7.7%と
  混在した結果。署名モデルはドメインモデルよりTPR+7.82%・ばらつき低下。失敗の70%超は
  静的解析で検出可能な誤り（存在しないAPI呼び出し49.0%、型不一致20.2%など）。
- ロードマップ（未実現の将来課題）：フィードバックループ、エージェント環境での評価、
  部分更新、そして「仕様を正とする品質ツール」——受入テストとそのハーネスの自動合成、
  仕様に照らして検証する静的解析エージェント・リンタ——の構想。
- 「構造化仕様が要求と高品質な生成の間の効果的な中間表現（intermediary）になる」という
  仮説文が、RC3の「実行可能な中間表現」という言い回しと表面上衝突する。なお論文自体は
  contractという語では主張していない（intermediaryという語）。

Task Contractとの違い：(1) SSDEの仕様が記述するのは**作る製品の振る舞い**であり、RC3が
記述するのは**作業そのものの責務**（責務境界・禁止副作用・文脈義務・許可能力・来歴義務・
エスカレーション）。これらの次元はSSDEに存在しない。(2) 仕様を入力としてそのまま渡すだけで、
仕様から実行計画・検証計画・実行環境を導出する機構（RC3のコンパイル）がない。文脈は実験者が
固定選択し、動的構築も充足判定もない。(3) 検証は製品テスト合格率のみで、境界違反・副作用・
証拠の有無への検証がない。来歴・Human介入方針も対象外。(4) 対象はコード生成のみで、
レビューや調査を含む一般タスクの制御面ではない。

### 2.2 RAIM（動的な文脈構築と副作用検証の具体機構で先行）

リポジトリ規模の機能追加（NoCode-bench Verified、114件）を対象にした実証寄りの論文。
4段階——構造木とimport関係によるファイル特定→コードグラフ（Package/File/Class/Functionを
節点、contains/imports/extends/callsを辺とするグラフ）上の多回検索とLLM選別による関数特定→
多設計生成（設計N=5から各パッチ）→影響分析（部分グラフの静的分析・回帰テスト・新機能テスト）
と5基準採点（関連性・構文/形式・上流安全・下流正しさ・回帰安全）によるパッチ選択。
Gemini-2.5-Proで成功率39.47%（従来最良比で相対+36.34%）、除去実験では多設計と選別が主要因。

Task Contractと重なるのは、「タスクに応じて文脈を動的に集める」「既存機能を壊す副作用を
検証する」が具体機構として実現されている点。違いは：(1) 入力は自然言語の文書変更であり
機械解釈可能な契約はない。(2) 文脈収集は埋め込み検索とLLM選別によるヒューリスティック
（発見的手法）で、宣言された義務からの導出ではない。不足の充足判定も、採否の記録
（RC3のContext Manifest相当）もない。(3) 影響分析は生成後のパッチ選別であり、事前宣言した
受入基準・禁止副作用への適合検証ではない。評価5基準は枠組み側の固定値。(4) 機能追加という
単一タスク種に特化し、来歴・権限・Human協調のモデルはない。

### 2.3 Symboleo（「契約の形式化」系譜の先行）

法的契約を義務（obligation）と権能（power）の集合として形式仕様化する言語。法オントロジー
（UFO-L）の拡張、O(debtor, creditor, antecedent, consequent)形式の義務、契約終了後も残る
存続義務、事前条件・事後条件、安全性・活性制約、状態機械による契約・義務・権能の生存期間
意味論（27公理、event calculus）、Prolog試作。義務違反が権能や新義務を発火させる構造は
RC3のEscalation Policyと構造的に似る。遵守監視とスマート契約コード生成・形式検証を構想。

対象は法的当事者間の関係であり、LLMの実行制御・文脈構築・ハーネス導出・来歴義務とは無関係。
ただし「機械解釈可能な契約」「義務と検証条件を持つ契約仕様」という概念自体はこの系譜
（Design by Contractを含む）が確立済みであり、RC3はこれを新規と主張できない。なお
SymboleoのコードはSSDE論文の実験対象3システムの一つ（SSDE文献[35]）で、両コミュニティは
隣接している。関連研究節の接続点になる。

## 4. 引用すべき3系譜

1. **契約の形式化の系譜**：Design by Contract、Symboleo（および義務・コミットメントの
   形式化研究）。Task Contractの概念的出自として引用し、「この伝統をLLM作業単位の統治へ
   移植し、実行系への導出源にしたこと」を貢献として明示する。
2. **構造化仕様駆動のLLM生成の系譜**：SSDE（およびSSDEが引用するspec-driven development
   一般）。「構造化した入力で生成品質・検証可能性が向上する」という主張はこの系譜へ譲る。
3. **リポジトリ規模の文脈構築・影響検証の系譜**：RAIM（およびAgentless・OpenHands、
   RepoGraph・CodexGraph等のコードグラフ手法）。「タスクに応じた動的文脈構築」
   「副作用・回帰の検証」の機構はこの系譜へ譲る。H2評価の比較対象候補でもある。

## 5. 譲る主張・守る主張

### 5.1 守る主張（3本のいずれも占有していない）【実測に基づく判断】

1. 実行タスクの責務を宣言する機械解釈可能な契約という成果物そのもの（九つ組：責務・責務境界・
   事前条件・文脈義務・許可能力・期待成果・受入基準・来歴義務・エスカレーション）。3本とも
   対象は「製品の振る舞い」または「法的当事者の義務」であり、「作業そのものの統治」を宣言する
   成果物がない。
2. 契約からの系統的導出（コンパイル）関係：文脈取得計画・レビュー観点・ハーネス構成・
   Human介入点・検証計画・来歴収集計画。SSDEは仕様を入力として渡すのみ（検証ツール生成は
   製品仕様基準かつ未実現の構想）、RAIMの文脈収集は宣言された義務からの導出ではない。
3. 来歴を事前義務として規定し、責務単位で完全性を検証すること。Symboleoのイベント記録は
   法過程の遵守監視であり、RC3の「要求↔契約↔文脈↔実行↔成果↔証拠」の追跡連鎖とは別物。
4. 契約適合レビュー（contract-conformance）と契約挑戦レビュー（contract-challenge）の二層。
5. 開発時と実行時の文脈（Specification Context / Execution Context）を同一のTask抽象で
   統一する見方。

補足：研究仮説H1〜H7に対応する測定（責務違反検出率、Evidence Coverage、責務外指摘率、
ハーネス構成工数、来歴完全性、介入局所化、状態変化への再構築）は、3本のいずれにもない【実測】。

### 5.2 譲る主張・言い換えるべき主張【推測を含む判断】

1. 「構造化した仕様をLLM入力にすると品質・検証可能性が上がる」——SSDEが先行（パイロット
   実証つき）。単独主張にしない。
2. 「自然言語の曖昧さが品質低下の根源」という問題設定の言い回し——SSDEの導入とほぼ同型に
   なるため、差異（SSDE＝製品仕様の曖昧さ、RC3＝作業統治の宣言の不在）を問題設定の段階で
   明示する。
3. 「タスクに応じた動的文脈構築」それ自体——RAIM等が具体機構で先行。RC3は「宣言された
   義務からの導出＋Manifest記録＋充足判定」で差別化する。
4. 「機械解釈可能な契約」概念そのもの——Symboleo・Design by Contractの系譜。引用の上で
   「LLM作業単位への移植と実行接続」を貢献とする。
5. 「副作用・回帰の検証」——RAIMの影響分析が先行。RC3は「宣言された禁止副作用・責務境界
   への適合検証」として一般化する点を差異とする。

言い回しの注意：positioning文の「executable intermediate representation」はSSDEの
「intermediary」と語感が被るため、争いのない「Task Contract as the control and
provenance plane for LLM-mediated workflows」を前面に出す【推測】。また「契約」という語は
定義節で法的契約（Symboleo）・プログラム契約（Design by Contract）と明確に区別する。
