# ReviewCompass 再スクラッチ開発計画

状態：計画案（実作業未着手）
作成日：2026-07-27
仮称：ReviewCompass3
想定配置：`/Users/Daily/Development/ReviewCompass3/`

## 1. 目的

ReviewCompass の有効なエッセンスと ReviewCompass2 で得た知見を引き継ぎつつ、
誤った骨子を継続利用せず、別ディレクトリでスクラッチ開発する。

開発方式は SDD とする。ただし、intent・requirements・design の作成とレビューを
支える既存ツールについては、正式仕様より先にブートストラップ基盤として実装し、
自己適用してよい。

## 2. 前提

- ReviewCompass2 は凍結状態を維持し、開発を再開しない。
- ReviewCompass2 の仕様・設計・承認状態は、新開発の正本として引き継がない。
- ReviewCompass と ReviewCompass2 は、読み取り専用の参照・証拠・比較対象とする。
- エッセンス抽出は「規則の抽出」に限定しない。
- 新開発で最初に実装する機能は、セッションログの記録と保全である。
- ブートストラップ実装は暫定物であり、後から確定する requirements・design に
  適合しなければ修正または置換する。

## 3. 開発原則

### 3.1 責務分担

- 人：目的、方針、承認、裁定、スコープ変更
- LLM：対話支援、意味理解、起草、レビュー、対応案
- 機械：列挙、採番、照合、被覆、状態遷移、記録、再開、送信制御

### 3.2 ブートストラップと正式実装の分離

先行実装には次の状態を明記する。

```yaml
lifecycle: provisional
normative_status: non-normative
promotion_required: true
```

ブートストラップ実装の現在の挙動を、そのまま requirements の根拠にしない。
requirements は intent と承認済みエッセンス台帳から導く。

### 3.3 TDD

各実装単位は次の順序で進める。

1. 期待される入出力からテストを作る。
2. 実装を書かず、赤を確認する。
3. テストだけをコミットする。
4. テストを変更せず実装する。
5. 全テストを緑にする。
6. 変異検査と実データでテストの有効性を確認する。
7. 実装をコミットする。

インデントは常に2スペースとする。

## 4. 参照資産の扱い

### 4.1 固定する参照状態

- ReviewCompass：エッセンス抽出開始時に参照コミットを固定する。
- ReviewCompass2：凍結コミットを固定する。
- 参照コミット、ファイル一覧、照合値を調査記録へ残す。

### 4.2 正本として引き継がないもの

- ReviewCompass2 の intent 第2版
- ReviewCompass2 の機能分割
- ReviewCompass2 の F-1〜F-6 requirements・design
- 既存文書の approved 状態
- 既存の「漏れなし」という判定

### 4.3 再検証する候補資産

- ReviewCompass2 のセッションログ実装とテスト
- 絶対パス混入 lint
- 利用者決定 UD-001〜093
- 現行の優位点一覧
- 抽出済みの1,416規則
- 既知失敗事例と変異検査の知見
- ReviewCompass のレビュー材料準備、実行、記録、復旧の各実装

ファイルを一括コピーせず、責務・契約・テスト単位で選別する。

## 5. 第0段：新リポジトリとセッションログ基盤

### 5.1 目的

以後の全判断・指示・失敗・承認を一次証拠として残せる状態を、他の仕様作成より
先に確立する。

### 5.2 最小リポジトリ骨格

- `AGENTS.md`
- `README.md`
- `pyproject.toml`
- `tests/`
- `tools/`
- `config/`
- 記録用の最小ディレクトリ
- 配布物とアプリ側成果物を区別する最小 manifest

骨格作成後、他の機能へ進まずセッションログ基盤を実装する。

### 5.3 実装対象

- 生セッションログの発見
- raw ログからの転写
- 人が読む要約
- 元ログ、取り込み範囲、照合値、ツール版の来歴
- 機微情報の伏字化
- 変更検知
- 追記専用の更新
- 再生成と照合
- 開始時・終了時フック
- セッションを使用しない期間にも動く定期保全
- 生ログの別領域への保全
- 保全先からの復元

### 5.4 保存区分

- 生ログ：リポジトリ外の保全領域
- 転写：リポジトリ外。生ログから再生成可能
- 要約：Git の管理対象
- 機微情報報告：リポジトリ外
- 来歴、照合値、保全結果：Git へ保存可能な範囲で記録

### 5.5 完了関門

- 生ログ消失後に保全先から復元できる。
- 同じ入力の再取り込みが冪等である。
- 転写・要約の改変を検出できる。
- raw → 転写 → 要約の来歴を追跡できる。
- 機微情報が Git の対象へ現れない。
- フック障害がセッションの開始・終了を妨げない。
- セッション非利用期間にも定期保全が動く。
- 実データと変異検査でテストの有効性を確認している。

本関門を通過するまで、第1段へ進まない。

## 6. 第1段：ブートストラップ・レビュー基盤

### 6.1 目的

intent、requirements、design を自己適用でレビューするための最小ツールを先に用意する。

### 6.2 実装対象

1. source universe の機械列挙
2. 対象・参照材料・必須材料の区別
3. 本文込みの材料束
4. digest、原文一致、stale 検査
5. 証拠閉包と材料被覆
6. 閉鎖 payload の生成
7. プロンプトと出力 schema の固定
8. 複数モデルまたは複数担当の実行
9. raw 応答の不変保存
10. 厳格な応答解析
11. 所見の統合と triage
12. 中断再開と成功成果の温存

### 6.3 主な移植候補

- `source_bundle.py`
- `source_scope_assurance.py`
- `source_scope_guard.py`
- `review_input_guard.py`
- `change_inventory.py`
- `risk_review_contracts.py`
- `risk_review_materializer.py`
- `risk_review_store.py`
- `assurance_pipeline.py`
- `run_risk_review.py`
- `trusted_review_send.py`

この一覧は調査母集団ではなく、抽出手続きが必ず発見すべき既知正例である。

### 6.4 完了関門

- source universe の入口が機械生成される。
- 既知正例がすべて候補へ現れる。
- 材料不足を正式な判定値として返せる。
- main と独立担当の材料選定経路が区別される。
- 材料変更後の送信を拒否する。
- payload、raw、parsed、triage の照合値が連結している。
- 外部送信が利用者承認と対象 digest に束縛される。
- 失敗した試行を残し、成功済み成果を上書きしない。

## 7. 第2段：エッセンス抽出

### 7.1 抽出対象

コードだけでなく、次を同じ母集団に含める。

- 実装
- テスト・fixture
- schema
- 設計・計画・issue
- セッション記録
- Git 履歴
- 実測結果
- 既知不具合
- 不採用案と不採用理由

### 7.2 抽出軸

1. 利用者目的・判断
2. 機能・能力
3. 手続き・処理順序
4. 不変条件・機械保証
5. データ・インターフェース契約
6. 失敗・停止・復旧
7. 実測知見・不採用判断

### 7.3 展開規則

```text
利用者操作・CLI
  → オーケストレータ
  → 呼出先
  → 入出力成果物
  → schema・validator
  → テスト・fixture
  → 設計・issue
  → 導入理由・失敗履歴
```

順方向だけでなく、被参照・呼出元・依存元の逆方向もたどる。

### 7.4 エッセンス台帳

各項目は次を持つ。

- 一意 ID
- 性質の記述
- 種別
- 根拠コミット・ファイル・位置
- 関係するテスト・失敗事例
- 依存項目
- `移植 / 再設計 / 不採用 / 後続`
- 判断理由
- 新システムでの受け先

### 7.5 完了関門

- 全追跡ファイルが `include / exclude / defer` のいずれかに分類されている。
- `unknown` がゼロである。
- 既知の移植漏れをすべて再発見できる。
- 不採用にも根拠がある。
- 独立担当が要約だけでなく生の参照材料から再判定する。
- 利用者がエッセンス台帳を承認する。

## 8. 第3段：intent

intent は人が主体となり、LLM が対話的に支援する。

記載対象を次に限定する。

- 何のために作るか
- 誰が使うか
- どのようなものを作るか
- 何をしないか
- 前提・制約
- 成功の判定基準
- 意図や制約が衝突したときの判定基準

細かな手続き、規則一覧、対応表、承認事務は intent の本文へ入れない。

ブートストラップ基盤でレビュー材料を作り、複数担当レビューを行う。材料不足が
報告された場合は、所見反映ではなく材料準備へ戻る。

## 9. 第4段：機能分割と requirements

### 9.1 由来

各要件は次の両方へ結線する。

- intent
- エッセンス台帳

受け先のないエッセンス、根拠のない要件、理由のない不採用を機械検出する。

### 9.2 記述内容

- 外部から観測できる振る舞い
- 入出力
- 停止条件
- 復旧条件
- 失敗時に保存されるもの
- 受け入れ条件
- 対象外

実装方法は requirements に固定しない。

## 10. 第5段：design とブートストラップ適合性監査

design 確定後、先行実装を項目ごとに分類する。

- `conformant`：そのまま正式昇格可能
- `adapt`：修正後に昇格
- `replace`：設計と不一致のため置換
- `defer`：初期対象外

ブートストラップ実装の挙動へ requirements・design を合わせることは禁止する。

既存のブートストラップテストは回帰テストとして凍結し、正式 requirements に基づく
受け入れテストを追加する。

## 11. 第6段：最小 E2E 縦切り

最初の正式実装で次の一本を通す。

```text
セッション記録
  → 小さな仕様変更
  → source universe
  → 意味単位
  → トレーサビリティグラフ
  → 決定的スライス
  → 閉鎖レビュー
  → triage
  → 利用者承認
  → 証跡
```

決定的な stub reviewer で再現性を確認してから実モデルへ切り替える。

### 完了関門

- 同一入力から同一の材料が生成される。
- source を1件落とす負例で停止する。
- 実行中の変更を stale として検出する。
- クラッシュ後に成功済み成果を壊さず再開できる。
- 既知失敗 fixture を再現し、防止できる。
- 一次証拠から承認まで追跡できる。

## 12. 第7段：正式機能の拡張

E2E 縦切り成立後、次の順で厚くする。

1. 意味構造化中核
2. レビュー実行エンジン
3. ワークフロー状態機械
4. reopen・maintenance
5. 記録・証跡基盤の正式昇格
6. 配置・配布
7. 適合性評価
8. 論文化・分析

## 13. 段の制御された終了

### 13.1 適用範囲

requirements に限らず、intent、feature-partitioning、design、tasks、
implementation を含むすべての段へ適用する。

### 13.2 終了種別

#### pause

一時停止する。段は完了扱いにしない。最後の有効成果物、未処理、再開地点を保存する。

#### cancel

現在の試行を打ち切る。試行中の成果物と理由は残すが、段は完了扱いにしない。

#### close-scope

残作業を不要と判断し、段のスコープを縮小して早期終了する。

### 13.3 close-scope の条件

残項目を全件、次のいずれかへ分類する。

- 完了済み
- 対象外
- 後続案件へ移管
- 意図的に不採用

分類後に次を検査する。

- 被覆
- 上流・下流整合
- 未決ゼロ
- 移管先の実在
- 利用者承認

すべて通過した場合だけ段を `completed` にできる。

### 13.4 状態遷移

```text
stage/in_progress
  ├─ pause  → stage/paused
  ├─ cancel → stage/cancelled
  └─ close-scope
       → 残項目の全件分類
       → 被覆・整合検査
       → 利用者承認
       → stage/completed
```

### 13.5 記録項目

- 終了種別
- 実行者・決定者
- 理由
- 最後の有効成果物と digest
- 未処理一覧
- 各未処理の処置
- 移管先
- 再開地点
- 後続段へ進めるかの判定

未処理を黙って残した段完了は fail-closed で拒否する。

## 14. 横断的な停止条件

次のいずれかが成立した場合、後続段へ進まない。

- セッションログの保全・復元が成立していない。
- エッセンス抽出の母集団が不明である。
- `unknown` 分類が残る。
- レビュー担当が材料不足を申告した。
- digest、原文、送信材料が一致しない。
- ブートストラップ実装が仕様判断を先取りしている。
- 既知失敗 fixture を検出できない。
- E2E 縦切りが成立していない。
- 段の未処理項目に処置がない。

## 15. 最初の実行単位

1. 新ディレクトリと Git リポジトリを作る。
2. 最小骨格だけを置く。
3. セッションログ基盤の移植候補とテストを棚卸しする。
4. セッションログ基盤の最初の赤テストを作る。
5. 赤を確認し、テストだけをコミットする。

この実行単位では、intent、requirements、design の作成を開始しない。
