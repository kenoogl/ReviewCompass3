### 1.1 操縦者の選択と役割の非対称

操縦者はClaudeまたはCodexから選べる。ただし、これは二つの方式が対称であることや、ClaudeとCodexの
名前を入れ替えれば同じ分担になることを意味しない。役割分担は意図的に非対称である。

| 項目 | `pilot: claude` | `pilot: codex` |
| --- | --- | --- |
| 操縦者 | Claude | Codex主担当 |
| 操縦者自身による実装 | 行う | 行わない |
| 実装担当 | Claude | ClaudeまたはCodex実装用サブエージェント |
| レビュー依頼 | Claude | Codex主担当 |
| レビュー実行 | Codex | Codexレビュー用サブエージェント |
| 完了管理 | ClaudeまたはHumanが指定した担当 | Codex主担当またはHumanが指定した担当 |

`pilot: claude`では、Claudeが操縦と実装を一体で担当し、Codexがレビューする。
`pilot: codex`では、Codex主担当が操縦、依頼、完了管理を担当するが、実装とレビューの実行は別担当へ
分離する。一方の方式から他方の役割を名前の置換だけで推定してはならず、必ず本書の該当列を使う。

## 2. 用語と固定する役割

操縦者（`pilot`）とは、Humanから作業項目を受け取り、上流文書を確認し、範囲を固定し、次の担当へ依頼し、
停止地点を管理する担当をいう。

実装担当（`implementer`）とは、固定された依頼に従って、テスト作成、実装、機械検証、実装証拠の記録を
行う担当をいう。

レビュー担当（`reviewer`）とは、実装を変更せず、上流文書、差分、テスト、証拠、実行後の状態を独立に
確認する担当をいう。

`pilot: claude`では、実装担当をClaude、レビュー担当をCodexに固定する。

```text
implementer: claude
reviewer: codex
```

`pilot: codex`では、実装担当をClaudeまたはCodex実装用サブエージェントから選べる。
Codex実装用サブエージェントは、Claudeに割り当てていたテスト作成、実装、機械検証、実装証拠の記録を
同じ境界で担当する。Codex主担当はレビューを依頼し、別のCodexレビュー用サブエージェント
（限定されたレビューだけを行う別実行単位）が実際のレビューを行う。

```text
implementer: claude | codex_implementation_subagent
reviewer: codex_review_subagent
```

### 2.1 `pilot: codex`のモデル対応

`pilot: codex`では、主担当とレビュー用サブエージェントのモデルを次のように交差させる。

| Codex主担当のモデル | レビュー用サブエージェントのモデル |
| --- | --- |
| `gpt-5.6-sol` | `gpt-5.6-terra` |
| `gpt-5.6-terra` | `gpt-5.6-sol` |

主担当はレビュー依頼、結果の受領、Git状態との照合、完了反映を担当する。レビュー用サブエージェントは、
実装結果の確認、テストの再実行、反証、判定記録の作成を担当する。

Codex実装用サブエージェントを選ぶ場合、そのモデルは主担当と同じ側に固定する。実装用とレビュー用は
別のサブエージェント、別の会話状態とし、レビュー用へ実装用の非公開の推論過程を渡さない。

レビュー用サブエージェントの起動時には、コミット済みの範囲固定文書、レビュー依頼、実装依頼、実装結果、
変更一覧、上流文書、実行段階台帳の該当部分を渡す。主担当の結論、期待する判定、非公開の推論過程を
渡さない。これらは起動時の固定材料であり、§7.1に従う追加探索を禁じない。判定記録には主担当とレビュー
担当のモデル名を記録する。

主担当のモデルが表の2種類以外である場合、または対応する反対側のモデルを利用できない場合、同じモデルや
別名のモデルへ黙って置き換えず、レビューを開始せずHumanへ報告して停止する。

## 3. Humanの決定

Humanは2026-08-11、次の分担を決定した。

- ClaudeとCodexのどちらも操縦者として選べるが、二つの役割分担は意図的に非対称とする。
- `pilot: claude`では、Claudeが依頼、実装、進行管理を行い、Codexがレビューする。
- `pilot: codex`では、Codexの主担当が依頼と進行管理を行い、実装担当はClaudeまたはCodex実装用
  サブエージェントから選び、反対側のモデルを使うCodexレビュー用サブエージェントがレビューする。
- ClaudeからCodexを起動する方式は、`pilot: claude`の場合に限る。
- `pilot: codex`でClaudeをレビュー担当にしない。

二つの方式で異なるのは、Humanとの窓口、範囲固定、実装依頼、修正管理を誰が行うかである。
レビュー担当の系統がCodexである点は共通とする。`pilot: codex`では、操縦、実装、レビューを同じCodex
実行単位へ戻さない。

## 4. 二つの方式の対応表

| 作業段階 | `pilot: claude` | `pilot: codex` |
| --- | --- | --- |
| Humanとの窓口 | Claude | Codex主担当 |
| 上流文書の確認 | Claude | Codex主担当 |
| 範囲固定 | Claude | Codex主担当 |
| 危険度の提案 | Claude | Codex主担当 |
| 危険度と再開の承認 | Human | Human |
| 実装依頼の作成 | Claude | Codex主担当 |
| テスト作成と実装 | Claude | ClaudeまたはCodex実装用サブエージェント |
| 実装証拠の記録 | Claude | 選択した実装担当 |
| レビュー依頼の作成 | Claude | Codex主担当 |
| 実装結果のレビュー | Codex | 反対側のモデルを使うCodexサブエージェント |
| 修正範囲の固定 | Claude | Codex主担当 |
| 修正実装 | Claude | 選択した実装担当 |
| 完了反映 | Humanが指定した担当 | Codex主担当またはHumanが指定した担当 |

`pilot: claude`では、Claudeが操縦者と実装担当を兼ねる。
`pilot: codex`では、Codex主担当が操縦者とレビュー依頼者を兼ねる。実装はClaudeまたはCodex実装用
サブエージェントへ、レビュー実行は反対側のモデルを使うCodexレビュー用サブエージェントへ分離する。

## 5. 共通の作業順序

二つの方式は、同じ順序で進める。担当だけを§4の対応表で切り替える。

| 順序 | 作業 | `pilot: claude`の担当 | `pilot: codex`の担当 |
| --- | --- | --- | --- |
| 1 | Humanから作業項目を受け取る | Claude | Codex主担当 |
| 2 | 上流文書、受入条件、変更範囲、禁止事項、停止条件を固定する | Claude | Codex主担当 |
| 3 | 必要なHuman承認を得る | Claudeが依頼する | Codex主担当が依頼する |
| 4 | テストを先に作り、失敗を確認してから実装する | Claude | 選択した実装担当 |
| 5 | 実装結果と証拠をコミットして停止する | Claude | 選択した実装担当 |
| 6 | 実装を変更せず独立レビューする | Codex | 反対側のモデルを使うCodexサブエージェント |
| 7 | 不合格なら修正範囲を固定して実装担当へ戻す | Claude | Codex主担当 |
| 8 | 合格後に完了反映する | Humanが指定した担当 | Codex主担当またはHumanが指定した担当 |

レビュー結果が`verified`（必要な証拠が揃い、実状態と一致する状態）になるまで、完了反映へ進まない。
`pilot: codex`では、順序4の前に§5.1の指示文品質関門を通し、順序5の後に§5.3の変更一覧を作る。
全順序を§5.2の実行段階台帳へ記録し、結果の保存と再実行は§5.4と§5.5に従う。

### 5.1 指示文品質関門

`pilot: codex`では、実装依頼、レビュー依頼、再実装依頼の指示文を、実行担当へ渡す前に品質確認する。
品質確認の対象は短い起動文だけでなく、コミット済み依頼書、対象、上流文書、出力要件、禁止事項、
停止条件を合わせた実効指示全体とする。

受入条件、禁止事項、停止条件、出力要件には、範囲固定時に重複しない固定識別子を付ける。識別子の
接頭辞は、受入条件を`AC-`、禁止事項を`NG-`、停止条件を`ST-`、出力要件を`OUT-`とする。監査、判定、
実装報告、レビュー結果は、この識別子ごとに結果と根拠を記録する。

品質確認は、機械検査と意味上の検査の二段階に分ける。

#### 5.1.1 機械検査

意味を判断する担当を起動する前に、決定的な処理で次を検査する。

1. 指示書が存在し、コミット済みで、記録したSHA-256と現在内容が一致する。
2. `AC-`、`NG-`、`ST-`、`OUT-`の必須項目が存在し、識別子に欠落、重複、未知の参照がない。
3. 参照材料が存在し、コミット済みで、記録したSHA-256と一致する。
4. 実行担当、対象、変更可能範囲、禁止範囲、停止条件、要求する結果形式が明記されている。
5. 指示文に記載したモデルと担当を利用でき、§2.1の対応に一致し、入力と出力の量がそのモデルの上限内に
   ある。
6. コードなどを囲む記号の開閉が対応し、参照材料の内容が指示文の一部として誤解されない構造である。
7. 外部送信を伴う場合、秘密情報の検査と、送信対象へ束縛されたHuman承認の確認が済んでいる。

一つでも不合格なら担当を起動せず、理由と修正対象を記録して停止する。形式上の欠落を指示文監査用
サブエージェントへ判断させて通過させてはならない。機械検査記録には、指示書、参照材料、要求集合の
SHA-256、検査結果、実行した検査器の版を残す。

実装依頼、レビュー依頼、再実装依頼は、同じ機械検査の入口を必ず通す。依頼種別ごとに検査処理を複製しない。
不合格時は、失敗した項目と、可能な場合は実行可能な復旧手順を示す。入力の自動切り詰め、自動分割、
自動修正は行わない。

CLI方式では参照材料の本文を指示文へすべて埋め込むことを要求しない。コミット、パス、SHA-256を固定し、
レビュー担当によるリポジトリ内の追加探索を許す。

#### 5.1.2 意味上の監査と判定

1. Codex主担当が機械検査済みの指示文案と参照材料を固定する。
2. 反対側のモデルを使う指示文監査用サブエージェントが、欠落、誘導、対象違い、材料不足、範囲逸脱を探す。
3. 各所見へ固定識別子を付け、影響する`AC-`、`NG-`、`ST-`、`OUT-`を列挙する。
4. Codex主担当が所見を反映し、機械検査を再実行する。
5. 監査担当とは別の新しい会話状態を持つ指示文判定用サブエージェントが、使用可否を判定する。
6. 判定担当は、監査所見の全識別子へ採用または不採用を一回ずつ対応付ける。欠落、重複、未判定があれば
   判定結果を不合格とする。
7. blocking所見がなく、全要求識別子について合格根拠が記録された指示文だけを実行担当へ渡す。

指示文監査用、指示文判定用、レビュー用は、それぞれ別のCodexサブエージェントとして起動する。Codex実装用
サブエージェントを選んだ場合も別の実行単位とする。Claudeを実装担当に選んだ場合は、これらとは別のClaude
セッションを使う。指示文品質確認の修正周回には、範囲固定時に上限を定める。同じ種類の指摘が2周続いた
場合は、文言修正を続けず、前提、材料選定、依頼の分割を見直すためHumanへ報告して停止する。

品質確認記録には、最終指示文のSHA-256、参照材料とそのSHA-256、監査担当と判定担当のモデル、所見、
要求識別子ごとの確認結果、反映結果、使用可否を残す。品質確認の合格は、実装、レビュー、外部送信、
完了を自動承認しない。

### 5.2 実行段階台帳と古い合格の無効化

`pilot: codex`では、範囲固定から完了までを実行段階台帳へ記録する。実行段階台帳とは、各段階の入力、
出力、担当、状態を順番に結び付ける記録である。最低限、範囲固定、Human承認の確認、指示文の機械検査、
指示文監査、指示文判定、実装、変更一覧、レビュー、再実装、再レビュー、完了の各段階を持つ。指示文の
機械検査、監査、判定には、実装依頼、レビュー依頼、再実装依頼の別と周回番号を付ける。再実装と
再レビューにも周回番号を付けて追加する。

各段階には、入力のSHA-256、出力のSHA-256、担当とモデル、開始・終了状態、未加工結果の参照、前段階の
識別子を記録する。段階の状態は、未開始、実行中、合格、不合格、停止中、古い状態のいずれかとする。

上流の指示書、参照材料、要求集合、モデル対応、実装結果のいずれかが変わった場合、変更地点より後の
合格を古い状態とし、完了根拠へ使わない。再開時は、最初の未完了または古い段階から始める。入力が変わった
ことを理由に、都合のよい過去の合格だけを残してはならない。

本節の機械処理がまだ運用経路へ接続されていない場合、開始記録へ`specified_only`（規則だけが存在する
状態）と明記し、機械保証済みと報告しない。実装と検証が済み、実際の起動経路から必ず呼ばれる状態だけを
`connected`（運用へ接続済み）と記録する。

### 5.3 変更一覧の機械生成

実装結果のコミット後、レビュー依頼を作る前に、基準コミットと実装後コミットの差を機械的に全列挙する。
変更一覧には、追加、変更、削除された全パス、未追跡パス、変更前後のSHA-256、基準と対象のコミット、
生成処理の版を記録する。実装担当の終了報告から変更一覧を転記しない。

変更一覧は事実の列挙だけを行い、範囲内か範囲外かを自動決定しない。範囲外の可能性があるパスは候補として
示し、Codex主担当またはレビュー担当が固定範囲と照合する。変更一覧のSHA-256をレビュー依頼と段階台帳へ
結び付ける。生成後に作業ツリーまたは対象コミットが変わった場合は古い状態とし、再生成する。

変更一覧はレビュー材料の入口であり、参照範囲を閉じるものではない。レビュー担当は、矛盾や選定漏れを
探すため、リポジトリ内の関連資料を追加で調べられる。

### 5.4 未加工結果と判定結果の分離

担当が実際に返した内容を未加工結果と呼び、そこから必要項目を抽出して検査した記録を判定結果と呼ぶ。
実装、レビュー、再実装の各結果について、この二つを分けて保存する。

未加工結果と対応する起動記録には、外から観測できる最終応答、起動識別子、終了状態、実行したコマンドと
終了コードを含める。非公開の推論過程を保存対象にしない。未加工結果は内容のSHA-256で識別し、一度保存
した内容を上書きしない。
機密情報を含む可能性がある未加工結果はGit外の保護された場所へ置き、コミットする判定結果には保存先の
種別、SHA-256、参照権限だけを記録する。

判定結果は最低限、担当とモデル、入力のSHA-256、状態、全要求識別子の結果と根拠、証拠のパスと位置、
所見識別子、変更パス、コマンドと終了コード、コミット、未解決事項、対応する未加工結果のSHA-256を持つ。
適用される受入条件は、関連するテスト、実装、記録の位置へ結び付ける。該当する成果物がない場合は、その
理由を識別子ごとに記録する。必須項目の欠落、識別子の重複または未知参照、解析不能があれば合格として
受理しない。解析に失敗しても未加工結果は保存し、再実行で上書きしない。実装時は、レビュー結果には既存の
`tools/bootstrap/raw_review_store.py`を再利用し、他の担当にも同じ上書き禁止の保存境界を拡張して、保存
処理を複製しない。

### 5.5 再実行、再開、結果再利用

過去の結果を再利用できるのは、結果が合格であり、現在の入力全体のSHA-256が記録済み入力と一致する場合
だけとする。入力全体には、基準コミット、指示書、参照材料、要求集合、結果形式、モデル対応、能力設定、
必要なHuman承認を含める。不合格、途中停止、解析不能の結果は再利用しない。入力が変わった場合は§5.2に
従い、影響を受ける段階以降を古い状態にする。

失敗後に同じ起動を黙って繰り返さない。再実行ごとに新しい試行識別子、理由、入力のSHA-256、再開段階を
記録する。別モデル、別認証、別経路へ自動で切り替えない。

再実装を同じ会話状態で続けるか、新しい会話状態で開始するかは範囲固定時に決める。指示文監査用、指示文
判定用、レビュー用は独立性を守るため毎回新しい会話状態とする。指示文品質確認と実装・レビュー往復の
上限回数をそれぞれ範囲固定し、上限を超えた場合はHumanへ報告して停止する。

## 6. 起動方向と受け渡し方法

役割分担と起動方法を混同しない。起動は作業を渡す手段であり、担当を決める根拠ではない。

| 操縦者 | 作業段階 | 起動方向 | 起動される担当 | 目的 | 方法 |
| --- | --- | --- | --- | --- | --- |
| Claude | レビュー | ClaudeからCodex | レビュー担当のCodex | 実装結果の独立レビュー | `pilot-driven-record-handoff.md`の固定起動文とCodex CLI |
| Codex | 実装 | Codex主担当からClaude | 実装担当のClaude | 固定済み依頼の実装 | 承認済みのClaude起動経路。完成までは`codex-claude-collaboration.md`のHuman中継 |
| Codex | 実装 | Codex主担当からCodex実装用サブエージェント | 実装担当のCodex | 固定済み依頼の実装 | §2.1のモデル対応と品質確認済み実装依頼 |
| Codex | レビュー | Codex主担当からCodexレビュー用サブエージェント | 反対側のモデルを使うレビュー担当 | 実装結果の独立レビュー | §2.1のモデル対応と品質確認済みレビュー依頼 |

直接起動が使えない、認証が切れている、または異常応答となった場合は、自動的に別の認証、別の送信先、
別の権限へ切り替えない。操縦者が事象と未実施範囲をHumanへ報告して停止する。

Human中継を使う場合、Humanはコミット済み記録の場所と開始・停止の合図だけを運ぶ。作業指示や判定内容を
チャットだけで作り直さない。

### 6.1 Claudeを実装担当にする場合の能力設定

`pilot: codex`でClaudeを実装担当にする場合、起動前に実装用の能力設定を固定する。能力設定とは、使用する
Claude CLIの版、モデル、認証方式、使用可能な道具、読み書き可能なパス、外部送信範囲、入力と出力の上限、
自動再試行の可否、機能拡張、事前・事後に自動実行する処理、外部機能の接続方式、会話の新規開始または
再開を一つにまとめた記録である。

疎通確認で使った全道具無効の設定は、ファイル変更とテスト実行を必要とする実装作業へ流用しない。Claude
実装用の能力設定を、Codexの指示文監査用、指示文判定用、レビュー用の能力設定と分け、必要最小限の権限を
担当ごとに固定する。実測したCLIの版、認証、利用可能な引数、道具の状態が固定記録と異なる場合は、Claudeを
起動せず停止する。

能力設定のSHA-256を実装依頼と段階台帳へ結び付ける。Human中継では、Codexが起動環境を機械確認できない
部分を`manual_relay_unverified`（人による中継のため未検証）と記録し、直接起動と同じ機械保証があるとは
報告しない。

直接起動では、Claudeの実行処理を開始する直前に、能力設定、入力全体のSHA-256、秘密情報検査、外部送信の
Human承認を再確認する。指示文作成時の検査結果だけで送信せず、直前確認との間に一つでも差があれば実行を
開始せず停止する。

## 7. 内容の正本

担当間で受け渡す作業指示、実装結果、レビュー結果の正本は、Gitへコミットした記録だけとする。
チャットの文章、起動時の短い指示、担当者の終了報告は、通知または開始合図として扱う。

ただし、Humanによる作業項目の指定、危険度の確定、再開・段完了の承認、意味的な裁定は、Humanの
チャット文言を正とする。操縦者はその文言を範囲固定文書または依頼書へ転記し、対象と内容を固定する。

### 7.1 CLI方式における閉包と発見性

CLI方式でも、一時ディレクトリなどを使って参照可能な資料を物理的に限定し、固定した資料だけを読める
状態にすることはできる。この制限を閉包強制という。したがって、CLI方式では完全な閉包が原理的に
不可能なのではない。

ただし、閉包を強制すると、固定した資料から漏れた関連文書、古い前提、実装上の不整合をレビュー担当が
独自に探して発見する力が失われる。現在はこの得失を踏まえ、閉包を強制せず、レビュー担当がリポジトリを
参照できる発見力モードを選択する。コミット済み記録を内容の正本とすることは、レビュー担当による追加の
探索を禁止することを意味しない。

発見力モードでは、参照範囲が固定資料だけに閉じていたとは主張しない。起動記録から参照した場所を
事後に照合し、固定資料の出自が機械的な抽出か人による選定かを記録する。閉包強制を将来導入するかは、
発見性を失う影響を実測したうえでHumanが別途判断する。根拠は
`records/development/2026-08-10-review-material-mode-decision-v1.md`とする。

## 8. 危険度が高い作業

外部送信、承認関門、検証器、改竄拒否など、誤った合格が重大な影響を生む作業は危険度`high`とする。

| 確認事項 | `pilot: claude` | `pilot: codex` |
| --- | --- | --- |
| 範囲と危険度の提案 | Claude | Codex主担当 |
| 危険度と実装開始の確定 | Human | Human |
| 実装 | Claude | ClaudeまたはCodex実装用サブエージェント |
| 完了レビュー | Codex | 反対側のモデルを使うCodexサブエージェント |
| 独立した反証 | Codexが新作して機械実行 | Codexサブエージェントが新作して機械実行 |

Codexのレビュー担当は、実装担当のテストだけに頼らず、上流文書から確認条件と反証を独立に導出する。
危険度`high`では、実装担当のテストにない反証を最低1件作り、機械実行する。
外部送信そのものを重複実行して反証にしてはならない。

## 9. 禁止事項

- `pilot: claude`で、Codexを実装担当、Claudeをレビュー担当にすること。
- `pilot: codex`で、Claudeをレビュー担当にすること。
- Claudeが固定済みの依頼範囲、受入条件、Human承認の意味を独自に変更すること。
- Codexがレビュー中に実装対象を修正すること。
- `pilot: codex`で、Codex主担当が自分で完了レビューを行うこと。
- `pilot: codex`で、主担当とレビュー担当に同じモデルを使うこと。
- `pilot: codex`で、Codex実装用とCodexレビュー用に同じサブエージェントまたは同じ会話状態を使うこと。
- 反対側のモデルが利用できないとき、同じモデルまたは別のモデルへ無承認で置き換えること。
- 指示文品質確認に合格していない実装依頼、レビュー依頼、再実装依頼を実行担当へ渡すこと。
- 指示文の機械検査に不合格のまま、意味上の監査または実行担当を起動すること。
- 入力が変わった後に、古い指示文監査、実装結果、レビュー合格を再利用すること。
- 未加工結果を上書きすること、または解析不能な結果を合格として扱うこと。
- 変更一覧を参照範囲の上限として扱い、レビュー担当の追加探索を禁じること。
- 疎通確認用の全道具無効設定を、Claudeによる実装作業の能力設定として流用すること。
- コミットされていない終了報告だけで、実装完了またはレビュー合格と判断すること。
- 直接起動に失敗した際、承認のない別経路、別の認証、別の送信先へ切り替えること。
- 一つの作業に本書と`role_neutral_pilot_review`を同時適用すること。

## 10. 作業開始時の固定項目

各作業は、開始時に最低限、次を記録する。

```text
collaboration_method: pilot_specific_claude_codex
pilot: claude | codex
implementer: claude | codex_implementation_subagent
reviewer: codex
closer: codex | claude | humanが指定した担当
work_item: <一つの作業項目>
```

`pilot: claude`では`implementer: claude`に固定する。`pilot: codex`でだけ、二つの実装担当から選べる。

`pilot: codex`では、さらに次を固定する。

```text
review_requester: codex_main
review_executor: codex_review_subagent
instruction_auditor: codex_prompt_audit_subagent
instruction_judge: codex_prompt_judgment_subagent
pilot_model: gpt-5.6-sol | gpt-5.6-terra
reviewer_model: pilot_modelと反対側のモデル
instruction_quality_model: reviewer_modelと同じ側のモデル
closer: codex_main | humanが指定した担当
base_commit: <作業開始時のcommit>
requirement_ids: <AC-、NG-、ST-、OUT-の固定集合>
result_contract: <実装・レビュー結果の形式とversion>
instruction_quality_round_limit: <正の整数>
implementation_review_round_limit: <正の整数>
reimplementation_context: new | resume
material_mode: discovery
mechanical_assurance_status:
  instruction_preflight: specified_only | connected
  stage_ledger: specified_only | connected
  change_inventory: specified_only | connected
  raw_result_store: specified_only | connected
  result_parser: specified_only | connected
  reuse_guard: specified_only | connected
  capability_preflight: specified_only | connected
```

`implementer: codex_implementation_subagent`を選ぶ場合、さらに次を固定する。

```text
implementation_executor: codex_implementation_subagent
implementation_model: pilot_modelと同じ側のモデル
implementation_context: review_executorとは別の新しい会話状態
```

`implementer: claude`を選ぶ場合、さらに次を固定する。

```text
implementation_executor: claude
claude_cli_version: <実測したversion>
claude_model: <固定したmodel>
claude_auth_method: <固定した認証方式>
claude_tool_profile: <実装用のtool許可設定>
claude_filesystem_scope: <読み書き可能path>
claude_external_send_scope: <承認済み範囲またはnone>
claude_session_mode: new | resume
claude_capability_profile_sha256: <能力設定のSHA-256>
claude_route_assurance: connected | manual_relay_unverified
```

`mechanical_assurance_status`の各項目が`specified_only`の作業では、該当処理を文書上の要求として扱うが、
その処理を機械保証済みとは報告しない。処理ごとに実装、試験、運用経路への接続が確認された後にだけ、
該当項目を`connected`へ変更できる。一部の処理だけが接続済みであっても、他の項目をまとめて
`connected`にしてはならない。

本書が定めるのは担当と受け渡し方法である。レビュー手順、テスト先行、Git規律、証拠規則、Human承認境界は、
`docs/development/work-review-protocol.md`と開発方針をそのまま適用する。
