## 1. 目的

RQ2 paired trialの**10ケース分の材料file**をrepositoryへ固定し、各ケースの**正解表を起草**する。
正解表の**確定は利用者**（計画§4-2。見積り1時間弱）であり、本作業は確定前の草案までを作る。

## 2. 正本範囲（成果物）

1. **材料fixture**：`tools/evaluation/fixtures/rq2/case-NNN/`（NNN＝001〜010）へ材料fileを
   新設。計画§1の割り当てに従う（実欠陥再構成3・人工欠陥4・合格系3）。
   - 各fileの冒頭に**全ケース共通の同一表示**を置く（複製材料であることの明示。欠陥の有無・
     正解の所在は一切示唆しない——事前走査§5-3）。
   - 合格系（C08〜C10）は共通表示を除き**複製元と1文字も違えない**。
2. **正解表record草案**：`records/development/`へ新設。ケースごとに——複製元path・複製元digest・
   注入操作（何をどう変えたか）・**期待Findingの要旨**・severity・根拠（材料内のpath/行）・
   誤検出の判定基準を機械確認可能な粒度で記す。
3. **材料digest表**：作成した全材料fileのSHA-256を`shasum -a 256`の出力そのままで正解表record
   へ収める（手書き転記をしない。転記後に`shasum -c`で機械照合する）。

## 3. 範囲外（後続作業単位）

- paired evaluation装置の実装・条件A/C/Dの資料配置の自動化・RQ2集計（後続2）。
- 実起動バッチ（後続3）・RQ2集計とEvidence固定（後続4）。
- 正解表の**確定**（利用者）。実験計画v1の測定定義・正解表配置の是正（事前走査§5の論点1・2。
  本作業では材料と草案を作るのみで、計画本体は改定しない）。
- 製品コード（`tools/`配下の実行モジュール）の変更。材料はデータのみ。

## 4. 受入条件

1. 10ケース分の材料fileが存在し、`shasum -a 256`で生成したdigest表が正解表recordの表と
   **機械照合で一致**する（`shasum -c`の終了コード0）。
2. 合格系3ケースが、**共通表示行を除いて複製元と同一**であることを機械確認する（`diff`）。
3. 欠陥ケース7件それぞれについて、**材料の中だけで検出可能**な形になっている（外部知識・
   digest計算を要しない）ことを正解表で説明する。
4. 全10ケースの冒頭表示が**byte単位で同一**であることを機械確認する。
5. `git diff --check`・意味単位commit・`work_unit_transition`合格。

## 5. 実施順序

1. 共通表示の文言を固定 → 材料fileの作成（ケース001〜010）。
2. digest表の機械生成 → 正解表record草案の起草 → digest機械照合。
3. 受入条件2・4の機械確認 → commit → 移行検証 → 完了報告（事前走査§5の論点を添える）。
