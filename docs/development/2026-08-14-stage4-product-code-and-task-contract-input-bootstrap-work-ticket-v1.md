## 5. 二つの分類軸

### 5.1 用途

| 値 | 意味 |
| --- | --- |
| `製品` | ReviewCompass3の利用者向け処理を実現するコード |
| `開発支援` | ReviewCompass3自身の開発、試験、移行、証跡作成、開発時の確認だけに使うコード |
| `共有` | 製品処理と開発支援処理の双方から使うコード |
| `用途不明` | 現在の利用先または上位根拠を確定できないコード |

### 5.2 今後の扱い

| 値 | 意味 |
| --- | --- |
| `採用候補` | 現在の実装を後続の正式採用判断へ渡せる候補。分類だけでは正式採用にならない |
| `保留` | 役割はあるが、上位根拠、保証、依存または成熟度が不足し、採用判断を後へ戻す |
| `使用停止` | 現在使わない境界が明示され、解除には別の利用者判断が必要 |
| `履歴のみ` | 現在の実行には使わず、過去状態の再構成だけに使う。現在treeに実行コードとして残る理由を要確認 |

【判断】用途と今後の扱いを一つの値へ混ぜない。例えば、`開発支援／採用候補`、`製品／保留`、
`共有／使用停止`は別々に成立し得る。正式製品コードは、`製品`または必要な`共有`と分類したうえで、
対象path、固定commitと内容識別値、利用処理、守る性質、試験、根拠文書を提示し、利用者が採用した集合だけとする。

## 6. 最初の製品処理候補の選定基準

後続の分類作業で候補を一件だけ示す。次の条件をすべて満たすものを優先する。

1. ReviewCompass3の利用者が得る結果を一文で説明できる。
2. 現在のGit treeに実行入口と主要処理が存在する。
3. 入力、出力、失敗時の停止が現在コードと試験から確認できる。
4. 到達するコード範囲を機械的に閉じられる。
5. 関連する要求候補、設計候補、試験を示せる。
6. 外部送信、不可逆操作、権限変更、使用停止中のIssue状態更新を必須にしない。
7. 未完成のTask Contract生成器、状態機械、許可機構を実装前提にしない。
8. 共有コードを製品専用と偽らずに分離できる。

複数候補が残る場合は、利用者価値、依存範囲の小ささ、現在保証の明確さ、戻しやすさから一件を推奨する。
外部送信入口、`issue_resolution_v4.py`、現在の保証と食い違う処理を候補にする場合は停止し、推奨前に利用者へ戻す。

## 7. 確認の深さ

### 7.1 全152 pathへ行う軽い確認

- Git treeからのpathと物体識別値の列挙。
- import、主な呼出し元、CLI入口、関連試験、直接参照文書の有無。
- 意味群、用途、今後の扱い、根拠、未確定点の記録。
- 重複割当、未分類、候補母集合外pathの混入がないことの機械照合。

### 7.2 最初の製品処理候補だけへ行う詳しい確認

- 入口から到達する全コードと共有境界。
- 入力、出力、状態変更、失敗、外部副作用。
- 利用先、守る性質、関連試験、根拠文書、内容識別値。
- 重複処理、再利用・共通化の可否、用途不明または未承認依存の有無。
- 現在コードと上流候補が食い違う場合の観測と利用者判断点。

### 7.3 到達しないコードへ行わないこと

最初の製品処理から到達しないコードには、用途と今後の扱いの分類を超える全文レビュー、変異検査、
全関数の要求対応、削除・統合案、修正案を一律に要求しない。

## 8. 実施方法の三案比較

| 観点 | 案A：既存Git・検索・一時的な構文解析 | 案B：既存の部分的な目録処理を転用 | 案C：新しい恒久目録・台帳を実装 |
| --- | --- | --- | --- |
| 単純さ | 高い。既存commandとリポジトリ外の一時処理だけ | 中。既存処理の保証範囲を読み替える必要 | 低い。設計・実装・試験が増える |
| 処理時間 | 152 pathの列挙と解析で十分小さい | 小さいが、誤った出力の確認が別途必要 | 初期実装が最も大きい |
| メモリ使用量 | 152構文木と関係表だけで小さい | 小さい | 台帳と中間表が増える |
| 頑健さ | Git treeを正本にし、独立再計算できる | 低い。処理呼出し目録は対象が限定され、既知の誤表示がある | 将来は高くできるが、今回中に保証できない |
| 変更範囲 | 作業票とEvidenceだけ | 既存処理の解釈変更または修正が生じ得る | コード・試験・schema・台帳へ拡張 |
| 保守負担 | 恒久物を増やさない | 転用後の意味を保守する必要 | 最も大きい |
| 戻しやすさ | 高い。読み取り結果を不採用にできる | 中。既存処理との役割混同が残る | 低い。新基盤の撤去が必要 |

【判断】案Aを採用する。Git tree、`rg`、Python標準の構文木、既存試験と文書参照を使う。
決定的な列挙・集計・照合は機械処理し、意味群、用途、今後の扱いはEvidenceに記録して利用者へ戻す。
比較のためだけの新しいscriptをrepositoryへ保存しない。

案Bは、`process_call_inventory.py`がprocess呼出しだけを扱い、禁止関数を許可関数名として返す既知反例を持つため、
全コード分類へ転用しない。既存Task Contract関連処理も正式利用前であり、今回の正本にしない。

案Cは、製品要求候補`REQ-WORKFLOW-009`の実装を第4段へ前倒しし、新しい恒久台帳を作るため不採用とする。
