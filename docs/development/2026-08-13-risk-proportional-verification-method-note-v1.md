# 重要度に応じた確認方法の運用メモ v1

- 作成日：2026-08-13
- 状態：`active_guidance`
- 用途：確認不足による手戻りを減らしつつ、軽い作業へ重い確認を一律適用しないための判断補助
- 適用状態：`AGENTS.md`を入口として使用する。既存計画の必須レビュー、作業票、承認境界を置き換えない

## 1. 背景と目的

【記録】静的なGit検査の扱いでは、内部関数の検査だけを見て、外部実装者を含む元の責務全体の確認が遅れた。
Python 3.13移行の作業票では、Homebrewの直接依存は確認したが、既定の追加処理と推移的依存の確認が開始前の
主担当調査から漏れ、独立開始前レビューで修正要となった。

【判断】共通原因は確認回数の少なさだけではない。中心判断が誤りになる条件を先に列挙せず、正常例や報告内容を
中心に確認したため、対象範囲の外縁、既定動作、間接的な影響への深掘りが不足した。

本メモは、作業の重要度と不確かさに応じて確認方法を変える案を示す。すべての作業へ独立レビュー、全試験、
複数モデルを一律に要求しない。

## 2. 重要度の決め方

重要度は、失敗時の影響と、確認対象の不確かさを組み合わせて決める。

- 影響：リポジトリ内で容易に戻せるか、共有環境や外部状態を変えるか、取り消せない結果を生むか。
- 不確かさ：単一の明示的な処理か、複数の呼出元、推移的依存、外部道具の既定動作、意味解釈を含むか。
- どちらか一方だけで決めず、影響が小さくても不確かさが高ければ一段上げる。

「依存閉包」とは、直接依存だけでなく、その先の間接依存を含む全体をいう。
「反証」とは、中心判断が誤りである可能性を意図的に試す確認をいう。

## 3. 重要度別の最低確認

| 重要度 | 主な対象 | 最低限の機械確認 | レビュー担当 |
| --- | --- | --- | --- |
| 低 | 文言訂正、局所的な読み取り、容易に戻せる一ファイル変更 | 差分、参照先、内容識別値、該当する検査 | 主担当の開始確認と完了確認 |
| 中 | リポジトリ内の可逆なコード・設定変更、複数ファイルの接続 | 影響先の列挙、対象試験、中心主張への反証1件 | 新規サブエージェントによる完了レビュー1回。意味変更が不明な場合だけ開始前レビューを加える |
| 高 | 共有処理、開発環境の交換、外部パッケージ取得、重要な意味判断 | 全呼出元または依存閉包、既定動作、副作用、復旧手順、中心主張への反証 | 新規サブエージェントの開始前レビューと、作業担当と異なる実行単位の完了レビュー |
| 重大 | 外部送信、秘密情報、履歴書換え、不可逆操作 | 実対象の確定、予行確認、復旧試行、権限境界、独立した反証 | 独立した二者の確認と利用者の最終承認 |

他社モデルは常時必須にしない。次のいずれかに当たる場合だけ追加候補とする。

- 中心判断が意味解釈に強く依存する。
- 一つの変更が複数の責務境界をまたぐ。
- 独立した二者の判定が割れた。
- 外部送信または不可逆操作を伴う。

他社モデルを利用できない場合は、利用者へ無断で代行を求めず、別の新規サブエージェントまたは利用者判断の
どちらが必要かを明示する。

## 4. 重要な判断ごとに残す最小材料

低重要度を除き、人の判断を左右する中心主張ごとに次の四点を残す。すべての細部へ適用せず、一作業の中心主張を
原則1件から3件に絞る。

1. 中心主張：何を安全、完全、使用可能と判断するのか。
2. 誤っていた場合の実害：何が壊れ、誰またはどの状態へ影響するのか。
3. 範囲全体の証拠：全呼出元、全利用経路、依存閉包、既定動作など、主張の範囲を覆う機械出力。
4. 試した反証：主張を否定する入力、経路、異常条件と、その終了コードまたは結果。

「すべて」「のみ」「副作用なし」「安全」と主張するとき、正常例が一件成功したことを範囲全体の証拠にしない。
作業担当の文章による報告も、それだけでは独立した証拠にしない。

## 5. 修正が発生したときの深掘り

最初の見落としが判明したら、その一箇所だけを直す前に、同じ種類の見落としを一回で機械列挙する。

| 最初に見つかった問題 | 修正前に確認する同種の範囲 |
| --- | --- |
| 依存を一件見落とした | 直接依存と推移的依存を含む依存閉包 |
| 呼出元を一件見落とした | 全参照、全呼出元、正規入口から到達する経路 |
| 外部道具の既定動作を見落とした | 公式ヘルプ、現在設定、予行確認、副作用を抑止する指定 |
| 責務を誤解した | 元要求、利用者判断、入力文書、実際の利用者または実行主体 |
| 数値または一覧が一件ずれた | 同じ生成元からの機械再集計と内容識別値 |

同じ原因で二回目の修正が必要になった場合は、自動的に修正を重ねない。目的、範囲、確認方法のどこを再判定するかと、
残る選択肢を利用者へ返す。

修正版のレビューは、原則として変更点と元の指摘が解消したかに限定する。変更していない部分は、証拠が古くなった
場合または修正の影響を受ける場合だけ再確認する。

## 6. 機械処理は警告を基本とする

新しい確認処理を作る場合は、開発を一律に停止する仕組みではなく、次の不足を示す警告から始める。

- 重要度が高いのに、中心主張、実害、範囲全体の証拠、反証のいずれかがない。
- 「すべて」「のみ」「副作用なし」と書かれているが、全列挙または依存閉包の結果がない。
- 外部状態を変えるのに、既定動作、予行確認、復旧手順のいずれかがない。
- 修正作業なのに、同種問題を列挙した結果がない。
- レビューが作業担当の報告だけを根拠にし、元ファイルまたは独立した機械出力を確認していない。
- 文書への導線を追加したが、後続の利用者決定、現行正本、実装との整合を確認していない。

警告が出ても、それだけで開発を禁止しない。利用者が理由と残る危険を確認し、進行または停止を判断できるようにする。
外部送信、不可逆操作、意味的裁定、段完了など、既存の承認境界は緩めない。

## 7. 現在の作業への適用例

Python 3.13移行は、外部パッケージ取得、`/opt/homebrew`への書込み、正式`.venv`の置換を含むため高重要度とする。
したがって、直接依存だけでなく依存閉包、Homebrewの既定動作、同じ抑止条件での予行確認、変更開始前の確認入力、
3.9環境への復旧手順を開始前に確認する。

【記録】作業票v2の修正後レビューは、利用者指示によりv1から変えたHomebrew手順だけを確認した。変更していない
部分は再レビューせず、先行判断を継承した。この扱いは、本メモ§5の「変更点を基本とする修正版レビュー」の例である。

## 8. 運用上の位置づけ

本メモは、作業開始時に確認の深さを決めるための判断補助として使う。立て直し計画§6や既存の
レビュープロトコルが定める必須確認と食い違う場合は、そちらを優先する。

文書への導線を追加するときは、内容を`現役`、`一部だけ有効`、`置換済み`、`履歴のみ`のいずれかへ分類する。
`現役`または`一部だけ有効`の場合は、後続の利用者決定と現行正本へ到達できるようにする。`置換済み`または
`履歴のみ`の場合は、現役の作業入口にせず、文書索引から置換先または履歴上の位置を確認できるようにする。

直ちに大きな台帳、状態機械、強制的な検査器を作らない。重要度は既存作業票の危険度判断を補助し、中心主張は
原則1件から3件へ絞る。不足検出を機械化する場合は警告から始め、既存の承認境界だけを停止条件として維持する。

警告処理の実装や、既存計画の必須事項を変える場合は、別の利用者判断を必要とする。
