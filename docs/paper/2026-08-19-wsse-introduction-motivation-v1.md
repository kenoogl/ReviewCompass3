## 1. 用語の解釈（音写の正規化・確認済み扱いとする読み）

| 利用者文言 | 本記録での読み | 英語表現の候補 |
| --- | --- | --- |
| ARエージェント | **AIエージェント**（LLMを核とするコーディングエージェント） | LLM-based coding agents |
| バイプコーディング | **vibe coding**（自然言語の指示だけで書かせ、仕様を明文化しない開発） | vibe coding |
| 要件設計、空分解実装 | **要件定義→設計→分解→実装**のフェーズ進行 | requirements → design → decomposition → implementation |

## 2. 動機の筋書き（確定）

1. **LLMエージェントの性能向上**により、コーディング支援の能力が実用域に達した。
2. **vibe codingの限界**：小さなプログラムなら成立するが、実用規模の開発では仕様の明文化が
   ないため利用が難しい。→**仕様駆動開発（spec-driven development）**が必要になる。
3. **仕様駆動開発の新しい問題**：要件→設計→分解→実装とフェーズを追うやり方は、フェーズが
   進むにつれて**文書量が増大**し、(a) 文書マネジメントの労力と (b) **人間の裁定負荷**が上がる。
4. この問題を**緩和するためにTask Contractを導入**した——機械解釈可能な責務契約を要求と実行の
   間に置き、レビューの文脈選択・検証・来歴を契約から機械導出する。
5. WSSE版（5頁）は**RQ1・RQ2の2つ**を中心に議論する（Task Contract全体の設計論はarXiv版へ）。

## 3. 動機と実測データの接続（序論の主張を裏づける数字）

動機の各要素に、本実験のどの数字が応えるかの対応。**序論の問題提起が §3〜4（評価）で
そのまま回収される**構図にする。

| 動機の要素 | 応える実測 | 出所 |
| --- | --- | --- |
| 文書量の増大がレビューを壊す | 無関係資料10 file・113KB追加で、ベースラインは入力**約4.0倍**・主題適中率**1.000→0.286**。Task Contract方式は材料選択**10ケース全件不変**・入力**+5.0%**・主題適中率維持（0.667→0.769） | RQ2確定集計（dataset v1・final metrics v1） |
| 裁定負荷の増大 | 実行前検査が欠落・競合9件を**全件、人が見る前に機械検出**（negative検出率1.0・誤停止0）——人の裁定を実欠陥だけに絞る | RQ1初回計測 |
