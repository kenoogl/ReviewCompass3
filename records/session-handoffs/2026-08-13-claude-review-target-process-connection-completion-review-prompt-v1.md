## 2. 確認する中心判断

実装が、Git差分を変更pathの正本として保ったまま、一つの分類入力から対象種別ごとの確認工程を
分けて生成し、漏れを警告できることを確認してください。第3段の試験整理や方針変更は確認対象外です。

次を確認してください。

1. 変更範囲が、失敗確認の試験一件と、許可された実装・案内三件だけか。
2. 失敗確認commitで対象試験が意図した未実装理由により失敗し、実装commitで同一の試験が成功するか。
3. 文書、製品コード、試験コード、検査コード、設定、構造化データが別の群で出力されるか。
4. 検査コードだけが最低危険度`high`となり、設定と構造化データが作業票の固有確認を持つか。
5. 未分類、余分、未知種別は警告付きの正常終了となり、未分類対象をコード変更として暗黙評価しないか。
6. 読めないJSON、重複path、安全でないpath、型不正、未知・重複する操作は入力不正となるか。
7. 外部送信、不可逆操作、意味的裁定、段完了が既存の利用者承認待ちに接続されるか。
8. 分類入力SHA-256、対象群、警告を含む計画全体が計画識別値で覆われるか。
9. 操作入口が分類入力以外のpath、担当数、周回数の上書きを拒否するか。
10. 対象試験、関連試験、公式全試験、四つの欠陥投入、独立した別計算の証跡が実状態と一致するか。

公式全試験は、可能なら次の正規入口で独立再実行し、終了コードと受領証を確認してください。

```text
.venv/bin/python3 -B -m tools.development.policy_test_runner \
  --suite full \
  --receipt <リポジトリ外の一時path>
```

失敗確認と四つの欠陥投入は使い捨て複製で確認し、成果物を変更しないでください。四つは、検査コードの
誤対応、Git差分一件の欠落、警告の消失、分類入力SHA-256を計画識別値から外す欠陥です。

## 3. 止める指摘の制限

止める指摘にできるのは次の四つだけです。同じ原因は一件にまとめてください。

1. 上位方針との矛盾
2. 必要な利用者承認の欠落
3. 誤った合否を生むことを機械で示せる欠陥
4. 作業範囲または入力・出力形式の境界違反

表現改善、将来拡張、命名の好み、実装の全面的な作り直しは止める指摘にしないでください。
本質から外れた過剰な修正案、追加の台帳、状態機械、強制関門、監視、追加のレビュー周回、
今回の保証に不要な試験を提案しないでください。問題がなければ余計な改善案を加えないでください。

## 4. 出力形式

平易な日本語で次だけを返してください。

1. 判定：`verified`または`blocked`
2. 止める指摘：件数、四分類の番号、根拠。無ければ0件
3. 報告不一致：件数と根拠。無ければ0件

6. 四つの欠陥投入と独立した別計算の結果
7. 公式全試験の件数、終了コード、受領証
8. 試した反証
