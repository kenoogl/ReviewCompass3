## 2. 独立確認

【実測】対象依頼v5と範囲固定v3は、それぞれ指定commit blob、現在file、記載SHA-256が一致した。各確認の
単独commandは終了コード0だった。

【実測】範囲固定v3 §3は12入力の一件でも不一致ならstaleとして開始前停止を要求する。依頼v5の§1、§2、
`AC-SR-CB-001`、`ST-SR-CB-001`が明示的に照合対象とするのは、対象scopeと§2の13材料だけである。
機械抽出の単独commandは終了コード0で、scope §3の12件中6件が依頼§2に無いことを示した。

【実測】6 pathは依頼の開始、受入、停止規則本文に現れず、scope §3全件を開始前に照合する規則もない。
たとえば計画fileだけが変化し、対象scope fileと依頼§2の13材料が不変なら、依頼の開始gateを通過する。

## 3. 判定

`SR-CB-001`の「対象と固定材料」と`AC-SR-CB-001`の「§1と§2の全入力」は、scope §3の12入力を暗黙には
含まない。したがって、所見は過剰ではなく採用を推奨する。

6 pathを依頼§2へ重複転記する必要はない。scope v3のcommit済みblobが表中pathとDigestを固定しているため、
依頼次版がその表を開始前gateとして全件消費すればよい。これにより二重台帳のdriftを避けられる。

## 4. 最小措置

依頼v5を書き換えず、次版に次の規則を追加する。

1. scope v3 §3の固定入力12件を対象commit blobから取得する。
2. 全12件で表中Digestと現在fileのSHA-256を開始前に照合する。
3. 一件でも不一致なら`reported_unverified`／`stale_input`で停止する。

これは12件を一括で閉じる措置であり、同類型の変種を一周で扱う。
