## 5. 検索結果からの現在判断

【判断】正式入口`tools/session_logs/read_only_entry.py`は、採用済み契約が指定する
`prepare_safe_result(raw_root, raw_log)`の追加先として**拡張候補**を維持する。G25の解析、伏字化、要約、
来歴生成は正式採用済みの既存経路を再利用し、同じ処理を新しい保存moduleへ複製しない。

【実測】G26には`storage._commit_outputs`、`preservation._write_atomic`、
`preservation._bind_inside_root`、`locking.exclusive_lock`、`config._validate_storage_boundaries`等の類似処理がある。
一方、G26全体は保留であり、`repository_root`省略時の既知反例が残る。これらは現在の契約が要求する
directory file descriptorからの相対開閉、symlink非追跡、所有者限定mode、二rootの状態遷移、削除確認値と
再試行を満たす正式証拠を持たない。

【判断】G26九fileを一括再利用しない。実装単位で必要になった関数だけを再評価し、契約を満たさない場合は
理由を付けて分離する。横断検索で見つかった`tools/common/digests.py`等も暫定表示であり、発見だけを理由に
正式製品コードの依存へ追加しない。再利用判断は、正式性と現在契約への適合を確認したものに限る。

## 6. 導線

【判断】製品コード着手前の順序を次のようにする。

1. 現在のコードから処理一覧と比較候補を再生成する。
2. 正式採用済みコード、暫定・保留コード、責務名の検索を分ける。
3. 対象fileを持つ検索記録の鮮度と再生成一致を機械確認する。
4. 候補ごとの再利用、拡張、統合、理由を付けた分離を作業Evidenceへ記す。
5. このコード管理作業を完了してから、別作業としてTDD実装境界を定める。
6. 独立開始前レビューは、コード管理の判断とTDD境界を別項目として反証する。

【判断】現時点では新しい包括的な入口、台帳、検査器、試験を作らない。既存処理に正式な一操作入口がないため、
今回の再生成順を一時的な機械実行で接続した。この手作業起動は正式なコード管理機能までの残余であり、
常態化させず、正式実装時の入口候補へ送る。
