## 1. 利用者判断

【記録】利用者は、根拠証跡に示した具体方針と、第3段開始前に対応する順序を確認した後、
「方針を承認する」と明示した。

【判断】次の方針を採用する。

1. 確認方法またはレビュー工程を選ぶ前に、対象を文書・読み取り調査、製品コード、試験コード、
   検査コード、設定、構造化された記録・宣言データ、外部操作へ分類する。
2. 対象が混在する場合、意味単位をfile種別だけで不自然に分割しない一方、レビュー工程と
   判定根拠は対象種別ごとに分ける。最も重い工程一種類へ丸めない。
3. 決定的な対象列挙と工程出力は機械処理し、責務に基づく意味分類は操縦役が行う。
4. 既存のレビュー計画生成処理は、未分類、分類と実差分の不一致、文書とコードの一括処理、
   検査コードの通常コード扱いを警告できる形へ接続する。
5. 警告だけを理由に開発を一律停止しない。外部送信、不可逆操作、意味的裁定、段完了など、
   既存の利用者承認境界を維持する。
6. 対象または種別が変わった場合は旧計画を古いものとし、レビュー担当は成果の合否より先に
   対象種別と工程の対応を確認する。

## 2. 対象別の工程

| 対象 | 採用する工程 |
| --- | --- |
| 文書・読み取り調査 | 差分、再読込み、参照解決、内容識別値、現行正本との意味整合。全試験や変異検査を一律に要求しない |
| 製品コード・試験コード | 期待する振る舞いの先行固定、関連試験。共有範囲と重要度に応じて全試験と独立レビューを追加 |
| 検査コード | 高重要度を原則とし、正常例、異常例、境界例、変異検査または同等の欠陥投入、独立した判定方法、開始前・完了レビュー |
| 設定 | 影響先、既定動作、関連試験。公式入口全体の合否を変える場合は重要度を上げる |
| 構造化された記録・宣言データ | 形式、識別子、版、内容識別値、上流参照、欠落、重複、改変入力。データ自体へコード用の変異検査を一律適用しない |
| 外部操作 | 利用者承認、実対象、権限、予行確認、結果記録、外部の事後状態 |

## 3. 採用した案と実装境界

【判断】既存文書への注意書きだけ、または軽量作業票への手書き欄だけでは、今回と同じ適用漏れを
十分に防げない。既存のレビュー計画生成処理で対象種別ごとの工程を出し、不整合を警告する案を採用する。
短い対象分類は既存の軽量作業票へ置き、新しい台帳、状態機械、強制関門は作らない。

【判断】実装は本判断と分けた一つの軽量作業票で行う。実装前に、既存処理の引数拡張、
Git差分からの自動分類、軽量作業票との照合という三案を比較し、必要な保証を満たす最も単純な方法を選ぶ。
レビュー計画生成処理は他の成果物の合否を支える検査コードであるため、高重要度として開始前レビューと
完了レビューを行う。
