## 3. 先行指摘の解消確認

### 3.1 `provenance.source_path`：解消

【実測】v2 §3.1は、正式入口の正常結果全体を保存せず、保存・再出力を許す項目を列挙した。
`provenance.source_path`は保存用派生物、manifest、`load-derived`出力、削除後監査情報から明示的に除外されている。
§5、§6、§8.4、§9.6、§10も同じ境界を保持する。記録IDはpathではなく内容から導出する。

【判断】一回の画面表示で許された相対pathを長期保存へ自動転用する矛盾は解消した。

### 3.2 片方の操作情報だけが残る途中失敗：固定fileについては解消

【実測】v2は両rootに`operation.json`を置き、記録ID、操作識別値、期待する内容識別値を持たせる。
片方だけに有効な`operation.json`が残っても、明示された記録IDの固定pathだけを直接読み、`incomplete`として
保存再試行または削除計画へ進める。確定印と反対側の操作情報は必須ではない。root走査、glob、推測削除は不要である。

【判断】指定された「raw側だけに有効な`operation.json`がある」反例は解消した。ただし§5で示すとおり、
書込み途中の一時fileまで含めた先行指摘全体は未解消である。

### 3.3 削除状態と確認値：解消

【実測】v2は、本文fileを削除する前に両rootの`operation.json`へ`deleting`と同じ削除確認値を書く。
片方の更新が失敗した場合は本文を削除せず、書けた側を再試行根拠として残す。本文と`commit.json`を削除し、
不存在を確認して`deleted.json`を再読込みした後にだけ、両側の`operation.json`を除く。

【判断】通常読込みの停止と削除再試行の根拠が分離され、削除確認値は本文削除完了まで失われない。
`deleted.json`は元の保持期限まで残し、期限後も明示削除だけを許すため、自動削除禁止とも矛盾しない。

### 3.4 正式入口からの値受渡し：解消

【実測】v2 §8.1は、同じ正式入口moduleに公開関数
`prepare_safe_result(raw_root, raw_log)`を追加し、標準出力を行わずに終了コードと安全結果を値で返す一つの方法へ固定した。
現在の`run()`と保存入口はこの同じ関数を使う。人の転記、標準出力の捕捉・再解析、外部process、G25からの別組立てを
禁止する。

【判断】現在の実行名、出力bytes、終了区分、安全検査、正式・安定表示を変えないことも前提、受入条件、停止条件へ
接続されている。既存入口を不必要に壊さず、値を渡す定義として十分である。

### 3.5 macOSの所有者限定権限とsymlink境界：ほぼ解消

【実測】v2は、保存rootと記録directoryを所有者だけの`rwx`であるmode 0700相当、通常fileを所有者だけの`rw`である
mode 0600相当とし、所有者不一致、group・other、追加ACLを停止条件にした。rootから固定fileまでをdirectoryの
file descriptorから相対的に開き、全構成要素でsymlinkを追わず、`O_NOFOLLOW`相当とopen後の所有者・種類・modeを
再確認できなければ停止する。

【判断】実装と受入を判定できる具体性がある。なお§5の「各root」は、§9.3の「各保存root」と整合させ、
0700相当を要求する対象が`sensitive_root`と`data_root`であると読む。`repository_root`まで0700相当を要求すると、
現在のrepositoryは実測0755であるため不要に拒否する。最終訂正時に「各保存root」へ語を揃えるのが明確だが、
止める中心は一時fileの削除閉包であり、別の仕組みや設計変更は要らない。

## 4. 指定された三反証

### 4.1 raw側だけに`operation.json`がある

【実測】raw側の有効な`operation.json`だけでも、記録ID、操作識別値、期待する内容識別値を確認できる。
状態は成功へ推測されず`incomplete`となる。`store`は同じ入力の場合だけ再開でき、`plan-delete`は確定印やdata側の
操作情報なしで当該記録の固定fileだけを計画できる。

【判断】反証不成立。root走査と推測削除は不要である。

### 4.2 data側の`deleting`更新だけが失敗する

【実測】raw側の`operation.json`に`deleting`と確認値が残り、data側が旧状態でも、状態優先順位は`deleting`である。
本文fileは両側が`deleting`になるまで削除されず、通常読込みも拒否される。次回はraw側に残った同じ確認値を根拠に、
data側の更新から再試行できる。

【判断】反証不成立。成功の誤表示、本文の先行削除、確認値の喪失は起きない。

### 4.3 `deleted.json`作成後に`operation.json`除去が失敗する

【実測】この時点では本文fileと`commit.json`の不存在を確認済みで、有効な`deleted.json`があるため、
通常読込みで本文を返すことはない。残った`operation.json`は`deleting`と同じ確認値を保持し、同じ削除操作の再試行で
除去できる。元の確認値を使う途中再試行と、保持期限後に新しい削除計画で監査印と残存操作情報を明示削除する経路は
区別されている。

【判断】反証不成立。監査印の保持、明示削除、途中再試行は両立する。

## 5. 残る止める指摘

### 一時fileが記録単位の削除対象に含まれない

【実測】先行レビューは、機微情報用領域へ「元記録またはその一時file」が残る反例を示し、途中fileも保持期限と
記録単位の片付け対象にする訂正を求めた。

【実測】v2 §7は「固定fileと同じdirectory内の一時file」を許すが、名前と対応を固定していない。§8.2は
「一記録の固定fileは§7に列挙したものだけ」とし、一時fileを状態判定へ含めない。§8.5の`plan-delete`は存在する
固定fileだけを対象とし、§9.17も削除対象を当該記録の固定fileだけに限定する。

【実測】次の反例が残る。

1. raw側へ有効な`operation.json`を置く。
2. 元記録を一時fileへ書いている途中で処理が停止する。
3. 再試行時、その一時fileは§7の固定fileではないため、予期しないfileとして変更せず停止するか、状態判定から無視される。
4. `plan-delete`と`delete`も固定fileだけを対象にするため、元記録を含む一時fileを削除できない。
5. root走査と推測削除は禁止されているため、契約内に安全な回収経路がない。

【判断】これは先行指摘と同じ原因の未解消部分であり、新しい問題を広げた指摘ではない。

【提案】契約文書だけを次の範囲で限定訂正する。

- 各一時fileの名前を、対応する固定fileと記録IDから決定的に一つへ固定する。
- `operation.json`に、存在し得る一時fileの種類と期待する内容識別値を持たせる。
- 一時fileを`incomplete`判定、保持期限、`plan-delete`の種類・件数、確認済み`delete`の対象へ含める。
- 一時fileだけが存在し、有効な操作情報がない場合は、引き続き推測削除せず停止する。
- §5の権限対象を「各保存rootと記録directory」と書き、§9.3と揃える。

これ以外のv2本文、三案、製品コード、試験、設定、既存契約、TODOは変更しない。
