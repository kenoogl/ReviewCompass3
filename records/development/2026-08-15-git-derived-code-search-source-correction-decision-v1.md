## 1. 利用者の指摘

【記録】利用者は、検索元が手作業で管理する固定一覧なら、新しいコードの追加ごとに版更新と一覧更新が
必要になり、保守負担と更新漏れを生むと指摘した。採用する形を次のように示した。

- 検索時に、現在のGit管理下にあるコードを機械取得する。
- 新しいコードも自動的に検索対象へ入れる。
- 検索時点の状態だけを、内容識別値とともに証跡へ残す。
- 過去の一覧は履歴として保持し、書き換えない。
- 正式、暫定、使用停止の区分は別に記録し、中央一覧へ毎回手作業で追加しない。

【判断】この指摘を採用する。先行検索の正式11 fileとG26九fileは、安全保存作業の対象を分けた時点検索で
あり、将来の全コード検索元または中央ライフサイクル一覧ではない。

## 2. 現行処理の実測

【実測】Work 4Aのsource universeは固定file一覧を持たず、`tools/**/*.py`という収集規則を持つ。
検索のたびに作業場所からPython fileを列挙するため、新規fileは規則上自動的に観測へ入る。一方、現行の
`_source_files()`はGitの追跡集合そのものを問い合わせず、作業場所に見えるfileを列挙する。未追跡のPython
fileがあれば検索元へ混入でき、Git管理fileの欠落があれば観測から落ち得る。

【実測】観測commit `9eb044a2876e31a2205e4ce0f9b5be13281c6881`について、次の二集合を別々に生成した。

1. `git ls-files`が返す`tools/**/*.py`。
2. source observation `c50ba7c...edbe`の`files[].path`。

両方とも151 fileで、順序付き一覧のSHA-256は
`be623c015a33ba64a8199dacd55485f137d84441042f0f5505405636a5524424`、双方向差分0件だった。
したがって先行検索の対象集合は今回のGit管理集合と一致する。

## 5. ライフサイクル区分

【判断】コードの検索対象と、正式・暫定・使用停止というライフサイクル区分を別にする。

- 検索対象：観測commitのGit管理コードから毎回自動生成する。
- 正式：対象コードを正式に受け入れた不変のDecisionと、その時点のpath・内容識別値から導く。
- 暫定・保留：候補表示、保留Decision、または正式採用Decisionがない現在コードとして扱う。
- 使用停止：使用停止Decisionと後継・停止境界から導く。
- 未分類：正式扱いにせず、人へ分類を戻す。

【判断】これらを一つの中央一覧へ複写しない。検索時に現在コード集合と関係するDecisionを照合する。
作業固有の固定pathは、その作業が何を確認したかを示す時点証拠として保持し、将来の検索対象を制限しない。

## 6. 先行検索結果への影響

【判断】先行検索の機械事実はstaleではない。今回のGit集合と観測集合が完全一致したため、1,580処理、
1,031比較群、正式11 file、G26九fileの検索結果は、観測commitに対する結果として維持できる。

【判断】ただし、正式11 fileとG26九fileの検索証明書を将来の全コード検索元または中央区分一覧として使う
解釈はstaleである。次回のコード実装前検索では、Git管理下の全コード集合を再生成し、新しいProfileと
Discoveryから対象作業の候補を導く。
