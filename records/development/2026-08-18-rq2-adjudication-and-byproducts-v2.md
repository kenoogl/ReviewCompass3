## 3. 議論から得た判別基準

裁定の過程で、指摘を分類する基準が1つ定まった。

> **依頼が渡したものだけを読んだとき、その指摘を避けられたか。**

避けられたなら誤検出、避けられないなら材料か依頼のどちらかの欠陥である。さらに、材料が間違って
いれば材料の欠陥、材料は正しいのに判断の前提が渡っていなければ依頼の情報欠落となる。

この基準の値打ちは、**「レビュアーの誤り」と「依頼の作りの不備」を分けられる**ことにある。
前者はレビュアー側の性能の話であり、後者は装置の改善点である。混ぜて誤検出率に数えると、
装置の改善余地が数字に埋もれる（§2.3がその実例である）。

## 4. 確定した採点語彙

正解表v2 §4の4語彙（検出／誤検出／責務外／非加算）を7語彙へ拡張した。装置
（`tools/evaluation/rq2_paired_trial.py`）へ実装し、RED先行で試験に固定した。

| 語彙 | 定義 |
| --- | --- |
| `detected` 検出 | 仕込んだ欠陥に当たった |
| `material_defect` 材料の欠陥 | 材料に実在する欠陥を正しく指摘したが、仕込んだものではない |
| `false_positive` 誤検出 | 材料にその問題は無い |
| `request_gap` 依頼の情報欠落 | 材料は正しいが、判断に必要な前提が依頼に無い |
| `off_subject` 対象外の指摘 | 材料としては正しいが、ケースの主題ではない |
| `out_of_scope` 責務外 | 材料の外側（複製元・実験の是非等）を論じる |
| `non_counting` 非加算 | 軽微（`medium`・`low`・`info`相当） |

## 5. 副産物——運用中の成果物に見つかった欠陥4件

実験は仕込んだ欠陥を測る目的で回したが、運用中の成果物の問題を4件表に出した。いずれも
**本実験の集計とは別**の是正対象である。本recordが観測記録に当たり、改善候補への登録と
仕分けは**未実施**である。

### 5.1 手順書の記述が実装と食い違う【機械確認済み】

`docs/development/prompts/session-log-record-run.md` 第1節は「合否は**このコマンド単独の終了
コード**で確認する（0=全系統成功、5=いずれか失敗）」と書く。実装
（`tools/session_logs/record_run.py` 149〜150行・203行）は、系統の状態が`ok`でも`partial`でも
ないときだけ失敗とし、`return 0 if summary["overall_ok"] else 5`を返す。つまり**どれかの系統が
`partial`でも包み役は0を返す**。第2節は`ok`と`partial`を区別しているので、その語彙で`partial`は
「成功」ではない。**第1節の「0=全系統成功」は実装の挙動を正しく書いていない。**

なおEvidence v1 §5の#1でClaudeは「対象が違うので矛盾ではない、ただし誤読しやすい」と書いたが、
**これは実装を確かめずに文面だけで判断した誤りであった**。ここに訂正する。

### 5.2 作業票の受入条件の表題が実態と違う

`docs/development/2026-08-17-launch-metrics-recoverability-work-ticket-v1.md` の受入条件4は
表題が「実機確認1回」だが、内容は「本作業票では試験（模擬実行）で代替する」である。受入条件は
後から充足を照合する対象なので、表題と中身のずれは照合を誤らせる。

### 5.3 終了コードの設計に不整合がある【機械確認済み・最も深い】

**発見の筋道**：レビュアーが指摘したのは§5.1（文書の食い違い）だけである。その裏を実装で
追った結果、根の設計に行き当たった。**指摘そのものではなく、指摘を起点にした調査の産物**である。

1. `tools/session_logs/cli.py` 39〜46行に段階を分けた終了コードの語彙がある——
   `EXIT_OK=0`／`EXIT_SENSITIVE_DATA=2`／`EXIT_NO_TARGETS=3`／**`EXIT_UNSUPPORTED=4`**／
   **`EXIT_FAILED=5`**／`EXIT_PRESERVATION_FAILED=6`／`EXIT_VERIFICATION_MISMATCH=7`／
   `EXIT_REGENERATION_FAILED=8`。
2. `tools/session_logs/read_only_entry.py` は**独自の語彙**（24〜25行で`EXIT_OK=0`・
   `EXIT_PARTIAL=3`）を持ち、185行で`partial`に**専用のコード3**を割り当てている。
3. `tools/session_logs/eventual_preservation.py` 898行は
   `return 0 if result.status == "ok" else 5` と書き、`partial`に**5**を返す。語彙の定数を
   取り込まず生の数字である。5は1の語彙では「失敗」を意味する。

**同じ部分系の中に終了コードの語彙が3つ並存し、同じ`partial`が入口によって3にも5にもなる。**
`partial`は手順書自身が「既知の正常状態」と書く状態であり、それを「失敗」のコードで知らせて
いる。「非対応」を意味する4が語彙に用意されているのに使われていない。

**連鎖**：子コマンドの終了コードが実態と合わない → 包み役は終了コードを判断に使えず要約JSONの
`status`欄を読む → その迂回を人へ説明する但し書きが手順書に入る → その但し書きを**4回中4回の
レビューが誤読する**。文書の食い違い（§5.1）は症状であり、根はここにある。

判断が要る点は3つ。`partial`に何を返すか（3へ揃える／語彙どおり4にする／0にして内容は要約JSONへ
委ねる）。既存の呼び出し側と保護試験（session_logs系330本）が5を前提にしていないか。3つ並存する
語彙を1つへ寄せるか。**範囲固定文書を立てる作業単位**として扱うべきである。

### 5.4 契約014の正準列定義に未記載の場合が2つある【新規・機械確認済み】

§1.1の適用で判明した。契約候補v2・v3の§7.1（正準列の定義）には次の2点が書かれていない。

- 従来判定を「Claude本文形式・Codex 2形式」の両方と定義しながら、前置recordの除外規則は
  「本文形式と判定しない」とのみ書く。前置recordがCodex 2形式として判定されうるかが不明である。
- 前置recordを読み飛ばしている途中で**入力の終端に達した**場合（判定可能recordが存在しない
  場合）の挙動が書かれていない。上限超過と打ち切りは書かれているが終端は書かれていない。

実装はfail-closedで安全側に倒れている見込みだが、**契約の本文には書かれていない**。契約は
受入済みであり、優先度は§5.3より低い。

## 6. 論文への含意

1. **主結果は採点の裁量に頑健である**（§2.2）。境界例をどちらへ倒しても、材料選択の不変性と
   条件B・Cの近接は動かない。査読で採点基準を突かれても主張が崩れない構造になっている。
2. **第一次採点と確定採点の差を公開できる**（§2.3）。採点語彙の粗さがレビュアー性能を6件の
   誤検出として過小評価していた、という具体例を示せる。
3. **主題適中率**（§2.1）が、「無関係資料を入れると誤りが増える」ではなく「**正しいが的外れな
   指摘が増えて主題が埋もれる**」というより正確な主張を可能にする。実測はベースラインが
   1.000→0.286、契約方式が0.667→0.769である。
4. **誤検出はほぼゼロだった**（85指摘中1件）。LLMレビューの弱点は「間違うこと」ではなく
   「**何について語るかを制御できないこと**」だと言える。文脈選択の設計が効く理由がここにある。
5. **実験が対象system自身の欠陥を4件検出した**（§5）。Task Contract経路のレビューが実運用の
   成果物に対して働くことの実例である。
6. **調査の起点としての指摘**（§5.3）。レビュアーの指摘は表層でも、それを起点に実装を追うと
   設計の根に届く場合がある。人と機械の分担の実例として書ける。
