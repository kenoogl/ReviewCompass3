# レビュー経路の設計方針メモ（契約010受入検討時の議論） v1

- 記録日：2026-08-17
- 参加：利用者（Human）とClaude（chat）
- 種別：設計方針の固定（利用者裁定を含む）。実装・契約変更は含まない
- 位置づけ：縦A・縦C・API経路pending判断の各契約定義時に前提として参照する入力

## 1. 機微情報検査の位置（縦Bに含めない）

【記録】利用者の裁定：

> repository全体がGoogleから読めることは許容しているので、機微情報の件は対策してもしようがないか。

- 帰結：縦B（CLI型・Reviewer自読）の起動時に機微検査の関門を追加しない。守りの境界は
  「機微情報をrepositoryへ置かない」既存運用＋読取り範囲のrepository限定（agy機械層・実測済み）に
  一本化する。依頼record 1件の検査はReviewerの自読範囲（repo全体）と非対称で、効果が薄い。
- 持ち越し：「書く瞬間に引っかける」価値は作成時にある。**縦A（依頼組み立て器）の機械検査へ
  内容機微検査（G20検知の流用）を含めることを、縦Aの契約定義時の論点とする**。

## 2. 複数Reviewerの突き合わせ（合議）の構成

- 利用者の問題意識：判定精度の担保のため、同一依頼をGoogleとOpenAIの両方へ投げる構成を考えたい。
- 現状：契約010は1起動＝1 Reviewer。ただしbackend登録形・複数担当対応の保存部品・宛先ごとの
  tier判定という土台は同報拡張を見込んで作られている。
- 経路の選択肢：(a) claude-subagent（第2縦切り・Tier 3・外部依存追加なし）、(b) codex CLI
  （疎通回復待ち・CLI型ファミリーへ自然に追加）、(c) `openai-api`（G20送信路。pending解除と
  応答解析・材料同梱の実装が前提）。
- 帰結：**合議は経路非依存の上位層（縦C領分）で、判定record同士の比較として作る**。運搬を
  1つのツールへ束ねる必要はない。

## 3. CLI型とAPI型の統合方針（利用者裁定）

【記録】利用者の裁定：

> ユーザ視点からは、CLI型のレビューとAPI型のレビューの両方を同じように使えるのはありがたいと思う。
> しかし、設計で無理に一緒にするのは悪手。

- 2経路は文脈構築の主体が根本的に異なる：CLI型はReviewerがrepositoryを自読（統制＝読取り範囲の
  機械制限＋操作記録）、API型は送信側が材料を組み立てる（統制＝機微検査・payload上限・台帳）。
  1つのbackend抽象へ押し込むと、抽象が太り、同じ`verified`の意味差（repo全読か送付束限りか）が
  隠れ、受入済み製品同士の保護境界が絡む。
- **確定した設計原則**：
  1. 共通化するのは**利用者接点**（依頼record→判定recordの流れ。将来は薄い入口振り分けまで）と
     **判定側規約**（判定schema・verdict語彙・判定recordの形式・tier宣言・事後照合の型）だけ。
  2. **運搬と文脈構築は経路ごとに分離**を保ち、各経路の統制をそのまま維持する。
  3. **突き合わせ（合議）は上位層**で、経路を問わず判定recordを読み比べる処理として実装する。
- API経路のadapter統合（backend化）は行わない。API経路が将来行うのは「判定record規約への準拠」
  だけであり、縦Bへの合流ではない。

## 4. 反映先

- 縦A契約定義：機械検査への内容機微検査の追加を論点に含める（§1）。
- 縦C契約定義：合議は判定record比較の上位層として定義する（§2・§3）。
- API経路pending判断：解除する場合も統合先はbackendでなく判定record規約への準拠とする（§3）。
