## 1. 目的

【判断】本Decisionの目的は、119件の直接確認対象を利用者へ一件ずつ裁定させることではない。安全保存機能を
実装する前に、正式な製品コードが既存の暫定処理へ依存してよい範囲を、八つの必要な働きごとに固定することである。

【判断】利用者が判断する対象は、機械列挙とコード確認を終えた後の意味上の依存境界だけとする。候補の列挙、件数、
重複、所在、契約との差は機械処理とLLMの意味分析で先に圧縮する。

## 2. 固定した根拠

【実測】正式検索はGit管理下のPythonコード152 file、1,600処理を対象に、八つの働きについて直接確認対象119件、
手掛かり1,223件、比較集団1,177件を分離した。119件は延べ件数であり、すべてを再利用可能と表示していない。

【実測】検索計画が明示した中心候補21参照を、重複を除いた19関数へ絞って実コードで確認した。正式・安定表示は
`tools/session_logs/read_only_entry.py:_safe_result`だけであり、その他の中心候補は暫定表示だった。

【実測】中心候補のコード集合に対し、次の契約上の安全条件を機械検索した。

- `O_NOFOLLOW`相当、`dir_fd`または同等のsymlink非追跡操作：該当0、終了コード1
- 所有者または追加ACLの検査：該当0、終了コード1
- `fsync`等の書込み同期：該当0、終了コード1
- 削除計画、`deleting`状態、削除確認値を保つ再試行可能な削除：該当0、終了コード1

【実測】既存の境界処理は`resolve()`後の範囲照合と`chmod`による権限変更を行う。採用済み契約は、rootから固定fileまで
symlinkを追わず、所有者・種類・mode・追加ACLを確認し、不適合なら書込み前に停止することを要求する。

## 3. 判断基準

【判断】再利用方法は次の基準で選ぶ。

1. 契約をそのまま満たす正式処理は、そのまま再利用する。
2. 小さい安全条件と対象試験を加えれば責務を満たす処理は、条件を補って再利用する。
3. 状態、失敗時の意味または安全境界が契約と異なる処理は、製品から直接呼ばず参考だけにする。
4. 直接対応する処理がなければ、新規実装する。

## 4. 八つの働きのHuman裁定

| 必要な働き | 裁定 | 対象と理由 |
| --- | --- | --- |
| 正式入口から安全な値を渡す | 条件を補って再利用 | 正式な`_safe_result`の許可項目選択を利用する。画面出力を介さず値を返す公開境界を追加し、保存用派生物から`source_path`を除く |
| 内容識別値 | 条件を補って再利用 | `canonical_json_bytes`と`sha256_hex`を、閉じた入力schemaと契約試験へ限定して利用する。`verify_provenance`は参考だけにする |
| 保存root・権限境界 | 参考だけ | 現行処理は権限を直して進み、契約が求める所有者、追加ACL、symlink非追跡、open後再確認を満たさない |
| 原子的な記録確定 | 参考だけ | 一時fileからの置換はあるが、new-only書込み、同期、二rootの状態確定、全file再読込み照合を一体で満たさない |
| 中断後の復旧 | 参考だけ | 既存cursorと収集処理の状態は、今回の`incomplete`、`committed`、`deleting`、`deleted`と同一でない |
| 検証付き再読込み | 参考だけ | 個別の来歴、ledger、cursor照合はあるが、二rootの操作情報、確定印、manifest、全内容識別値、保持期限をまとめて確認しない |
| 再試行可能な削除 | 新規実装 | 直接対応する既存処理がなく、削除確認値と`deleting`状態を完了まで保持する処理もない |
| 同時更新の排他 | 参考だけ | 既存`exclusive_lock`は別のlock fileと親directoryを作り、契約の固定file集合と保存root・権限保証へそのまま接続できない |

【判断】合計は、条件を補って再利用2、参考だけ5、新規実装1、そのまま再利用0とする。参考だけとした既存関数を、
正式な安全保存処理の実行時依存へ入れない。
