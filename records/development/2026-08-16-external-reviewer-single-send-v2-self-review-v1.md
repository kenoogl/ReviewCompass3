# 外部レビュア一回送信 契約候補v2 自己レビューと文脈整理 v1

- 実施日：2026-08-16
- 担当：Claude（契約作成者による起草側の事前検討。独立確認の代替ではない）
- 方法：Definition Challenge型の固定4質問（定義の欠落・境界の過小・禁止の漏れ・依存の忘れ）を全条項へ適用
- 位置づけ：外部レビュー5段手続きの第1段・第2段。訂正根拠および依頼promptの文脈材料

## 1. 発見（修正要級——契約v3で訂正する）

### SR-1 累計上限の計数rootが未固定（定義の欠落・境界の過小）

【実測】v2 §7.3は累計送信試行を「台帳の試行record件数」で数えるが、台帳の置き場所は送信指示の
`output_root`（毎回変えられる絶対path）である。output_rootを変えれば計数が分かれ、累計100件上限が
機能しない。

**訂正**：台帳rootを`{repository_root}/.reviewcompass/egress-ledger/`へ契約固定する。台帳・応答・結果は
全てこの一箇所に着地し、累計はこのdirectoryの試行record件数で数える。送信指示から`output_root`を削除する。
副次効果として台帳fileはrepository内に置かれ、通常のcommit手順で履歴に残るため、git履歴自体が監査線になる。

### SR-2 provider別のHTTP要求本文形式が未固定（定義の欠落）

【実測】v2 §7.1はhost・経路・認証headerを固定するが、要求本文のJSON形を固定していない。特に
anthropic-apiの`/v1/messages`は`max_tokens`が必須であり、値の選択が実装者の後決めになる。

**訂正**：3 providerの要求本文の固定形（modelとpayload本文だけを埋める最小template、anthropicの
`max_tokens`は8192固定、`anthropic-version`は`2023-06-01`固定）を§9へ付表として固定する。

### SR-3 リダイレクト追従・proxy・TLS検証の禁止が未記載（禁止の漏れ）

【判断】HTTP clientは既定でリダイレクトへ追従し得るため、宛先host固定でも3xx応答で鍵つき要求が別hostへ
向かい得る。また標準libraryは環境のproxy設定（`https_proxy`等）を暗黙に読むため、「環境値解決は3変数だけ」
の原則が実装の既定動作で破られ得る。TLS証明書検証の無効化も明示的に禁じられていない。

**訂正**：§7.1へ「リダイレクトへ追従しない（3xxは`http_error`として停止・応答保存）」「環境のproxy設定を
使わない」「TLS証明書検証を無効化しない」の3禁止を明記する。

### SR-4 応答sizeの上限が未定義（定義の欠落）

【判断】応答の保存に上限がなく、異常応答でdisk・repositoryが際限なく膨らみ得る。

**訂正**：応答は16,777,216 bytes（16 MiB）を上限とし、超過は`response_size_exceeded`（source `network`・
終了コード7）で停止する。試行recordは残存し、応答fileは作らない。

## 2. 発見（限界として明示する——設計は変えない）

### SR-5 「commit済み」の機械強制はmoduleの外にある

moduleはGit操作を禁止されているため、検査できるのは「宣言digestと実bytesの一致」まで。commit済みで
あることの照合は、送信指示を作成する手続き（操縦LLMがGitで機械確認する）の義務である。§7.2へこの分担を
明記する。

### SR-6 出力先事前検査の対象名の明示

事前検査で不存在・既存を確認する対象（台帳root、試行・応答・結果の3 file名）を§10へ明示する。

## 3. 発見（既知の除外——本縦切りでは扱わない）

- SR-7：allowlistに`.reviewcompass/`配下（台帳・改善候補record）を含めない。本縦切りのレビュー用途では
  不要と判断した。必要になれば契約改定で扱う。
- SR-8：応答（外部AIの出力）をrepositoryへcommitすることになるが、これは判定recordの従来運用と同じであり、
  size上限（SR-4）が肥大を抑える。

## 4. 文脈整理（依頼promptへ含める判断済み事項・範囲外）

- **判断済み（レビューで蒸し返し不要）**：送信ごとの人の確認なし（利用者が経緯を踏まえ決定、§2に記録）。
  宛先3 provider切り替えと独立性検査（利用者指示）。台帳のrepository内配置（SR-1の訂正、本自己レビューで判断）。
- **範囲外（「無い」という指摘は不要）**：応答解析、監査自動化、旧egress設計との統合、複数送信・連鎖、
  Gemini以外へ広げる宛先追加。
- **レビュアへ特に依頼する深掘り**：(1) SR-1〜4の訂正が一意に閉じているか、(2) 私が見落とした欠陥類型
  （特に鍵・内容が意図外へ漏れる経路、台帳の計数を欺く経路）、(3) 台帳をrepository内へ置く判断の副作用。
