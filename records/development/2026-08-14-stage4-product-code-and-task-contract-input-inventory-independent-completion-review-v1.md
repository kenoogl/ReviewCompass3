## 2. 止める指摘

### ST4-INV-001 最初のTask Contract入力と能力境界が固定されていない

- 区分：`blocking`
- 確認段階：`completion`
- 根拠類型：1「上流authorityであるPlanとの矛盾」

【記録】立て直し計画v5第4段は、次を必須作業と完了確認にしている。

1. 既存のTask Contract構想から、最初の製品作業に必要な最小項目だけを選ぶ。
2. 後回しにする項目、未完成の生成器、状態機械、許可機構を明示する。
3. 独立レビューで、最小項目から最初の契約を定義できるか確認する。

【実測】Task Contract中心構想§4.9は、最小核をIdentity、Responsibility、Preconditionsまたは
Context Obligations、Expected Outputs、Acceptance Criteriaとし、実行可能な契約ではBoundary、
Allowed Capabilities、Provenance Obligations、Escalation Policy、版付きdependencyを加える。

【実測】EvidenceにはG25の責務、入力、出力、停止、コード境界、試験が個別に書かれているが、上記項目を
どれだけ採用し、各項目をどの固定入力で満たし、何を第5段へ後回しにするかを対応付けた記載がない。
関連語を機械検索した結果、G30の群名以外に最小項目の選定はなかった。そのため、現状のEvidenceだけでは
「未完成基盤を必須にせず、G25の最初の契約を定義できる」と確認できない。

【実測】さらにEvidence §8.3は、環境依存の伏字化規則が指定された場合に、G25がhome、利用者名、host名を
メモリ上で解決すると記す。しかし、`tools.session_logs.pipeline.prepare_artifact`から到達する40関数には、
`resolve_environment_rules`、`Path.home`、`socket.gethostname`は含まれない。G25は渡されたpattern規則を
使うだけであり、環境値の解決はG25外の呼出し側処理である。これは、最小項目のAllowed Capabilitiesと
Preconditionsを対応付けていないために生じた報告不一致である。

【提案】最小の限定訂正は、対象Evidence一件だけへ次を加えることである。

1. G25について、上記の最小核と追加5項目を、既存の§8の事実へ対応付けた一表を加える。
2. 各項目を`固定済み／第5段で定義／未解決`に分け、未完成の生成器、状態機械、許可機構を前提に
   しないことと、後回し項目を明記する。
3. その表から、最初の契約案を第5段で定義できるかを結論として記す。契約自体は第4段で作らない。
4. 環境参照の行を、G25自身は環境値を解決せず、解決済みpattern規則を入力として受ける境界へ訂正する。

新しい台帳、検査器、試験、関門、Task Contract実行基盤は作らない。他の集計と分類をやり直さない。
