## 1. 機能と用途

【判断】固定するのは検索対象fileではなく、作業ごとに必要な働きを定義し、現在のGit管理コード全体から
直接関係する処理と共通内部部品を導く方法である。用途は、新しい処理を作る前に、別名・別機能内にある
再利用可能な部品を見落とさず、重複実装を避けることである。

## 2. 現状と不足

【実測】現行`reuse_search_record.search_existing_routines`は、作業計画の`target_paths`と
`target_symbols`に一致した処理、その直接の呼出し先・呼出し元、比較群を返す。比較群は現在のGit管理
コード全体から作られるが、必要な働き、必要な副作用、禁止する副作用、既知の参考処理を作業単位で
対応付ける構造を持たない。

【判断】安全保存用の20 pathは当該作業の時点入力として正しいが、将来作業の固定対象ではない。今回の
変更は中央一覧を追加せず、作業別計画の入力単位をfile中心から必要な働き中心へ改める。

## 4. TDD開始前の実装境界

### 境界1：一つの必要な働きから候補を導く

- 入力：働きID、責務、既知の参考path・処理、処理名の手掛かり、必要・禁止の構文副作用。
- 失敗確認：現行検索へ同入力を渡せず、別名の比較群member、禁止副作用、成熟度表示を返せない。
- 最小実装：既存ProfileとDiscoveryだけから、参考処理、全member、構文特徴一致を決定的に返す。
- 完了：候補ごとに根拠、禁止副作用との衝突、sourceに明記された成熟度を返し、採否を決めない。

### 境界2：一操作入口と作業別計画schema 2

- 入力：複数の必要な働きとnew-only証明書pathを持つ作業別計画。
- 失敗確認：現行入口はschema 2を拒否し、必要な働きの未対応を結果へ出せない。
- 最小実装：同じcommit、観測、処理一覧、比較候補から全働きを検索し、一つの外部正本と証明書を生成する。
- 完了：働きごとの候補数、未対応、内容識別値、Human裁定待ちに加え、観測、処理一覧、比較候補、各検索、
  全体の実行時間を一回で返す。時間は変動する観測値なので検索recordの内容識別値へ含めない。

【判断】二境界は別機能に分けず、同じコード管理機能内の順序付き小単位とする。製品のTDD実装境界確認とは
別であり、同じ合否へ統合しない。

## 5. 機械検索とHuman判断の境界

【判断】自然文だけから機械が責務を推測しない。作業ごとの必要な働きはHumanが確認する。機械は現在の
Git管理コード、処理一覧、構造比較、直接関係、構文副作用から候補を導く。正式・暫定・使用停止は、sourceに
明記された成熟度を観測として表示するが、Decisionを推測して上書きしない。採用、不採用、修正利用はHuman
裁定待ちとする。
